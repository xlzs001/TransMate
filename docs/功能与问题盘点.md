## 二、BUG 清单

### 严重（会导致功能异常、白花钱或持续耗电）

#### BUG-1 「顶栏」位置会陷入更新死循环 —— **本轮最严重的一条**（v3.9.12 已修）

- **位置**：`timezone.js` `attachRoot()`
- **问题**：当显示位置选「联系人标题栏右侧」时，每次 `update()` 都无条件执行 `header.insertBefore(root, actionArea)`。
- **根因**：另外两个位置分支都有"位置不对才动"的守卫（`root.parentElement !== header`），**唯独这个分支没有**。而 `insertBefore` 会把已连接的节点先移除再插入，即使位置完全没变，也会产生 childList mutation record。
- **为什么会被自己触发**：`MutationObserver` 观察的是 `document.documentElement`（`subtree: true`）。过滤器只排除 `#wat-region-time-root` **内部**的改动（`target.closest('#wat-region-time-root')`），而 mutation 的 target 是 WhatsApp 的 header —— 它是我们 root 的**父级**，`closest` 匹配不到 → 不被过滤 → 判定为"页面变了" → `scheduleUpdate()` → 180ms 后 `update()` → 再次 `insertBefore` → **闭环**。
- **影响**：选择该位置的用户陷入约 **180ms 一次**的更新循环。每轮都要读 storage、跑 `resolveContactFacts`（含强制布局的 `getBoundingClientRect` 和 franc 语言识别）、重渲染面板。表现为页面持续卡顿、CPU 占用高、笔记本耗电发热。
- **修复**：把第三个分支也改成 `else if (config.watPosition === "header" && root.parentElement === header)`，或统一用一个"位置是否已正确"的判断。
- **状态**：机制已确认（两处守卫缺失 + 观察器过滤器不覆盖父级 mutation）。建议修完在浏览器里实测一次确认。

#### BUG-2 目标语言是 zh-CN 时，中文原文**永不跳过**（v3.9.12 已修）

- **位置**：`timezone.js` `shouldSkipChatTranslation()`
- **问题**：`if (targetBase === "zh" && normalizedTarget.includes("-")) return false;` —— 这一行直接返回"不跳过"。
- **根因**：默认目标语言是 `zh-CN`（含 `-`），所以这个条件**恒成立**。而中文经 `detectByScript` → `cmn` → `LANGUAGE_BY_ISO3.cmn = ["zh", "中文"]` → `detected.code === "zh"`，与 `targetBase` 相同、置信度 100 ≥ 78 —— 也就是说**如果没有这一行，中文本来会被正确跳过**。
- **影响**：中文消息（包括用户自己发出的）被送去翻译成中文。后果有两个：① 白花钱；② 原文下方插入一行几乎相同的中文，聊天区出现重复气泡。
- **注意**：这一行大概是为 `zh-TW` 加的（简体 → 繁体确实需要转换），但它连带把 `zh-CN` 也覆盖了。
- **修复**：只在 `targetCode === "zh-TW"` 时放行，`zh-CN` 走正常跳过逻辑。
- **状态**：逻辑链已逐行确认。

#### BUG-3 「测试连接」对推理模型必然失败（v3.9.12 已修）

- **位置**：`background.js` `testProvider()`
- **问题**：`callProvider` 的 `maxOutputTokens` 默认值是 **800**，而 `testProvider` 没有传这个参数。
- **根因**：推理模型（`/^(?:gpt-5|o[134](?:-|$))/i`）的 `max_completion_tokens` 是"思考 + 正文"合算，800 会被思维链吃光 → `finish_reason: "length"` → 抛错「AI 返回内容达到长度上限」。
- **影响**：配 gpt-5 / o1 / o3 / o4 的用户点「测试连接」看到的是"达到长度上限"，会误判成 Key 填错或模型名不对，反复折腾。而真正的翻译路径**已经**走了 `estimateOutputTokens`（预算正确）—— 只有测试这一条路漏了。
- **修复**：`testProvider` 也走 `estimateOutputTokens(...)`，一行。
- **状态**：已确认（`callProvider` 默认值 800 在签名里，调用点确实没传）。

#### BUG-4 数字输入框清空后会存成**下限值**，不是默认值（v3.9.12 已修）

- **位置**：`options.js` `clamp()`
- **问题**：`Number("")` 等于 `0`，而 `0` 是有限数，所以 `fallback` 永远不会生效。
- **影响**（清空对应输入框后保存）：
  - 水平微调 → `-400px`（标签被推出屏幕外）
  - 垂直微调 → `-300px`
  - 显示大小 → `75%`
  - 译文大小 → `10px`
  - 连续空格次数 → `2`
  - 判定时间 → `500ms`
- **说明**：`fallback` 参数实际上是**死代码** —— `type="number"` 的输入框在内容非法时 `.value` 返回空串，永远不会返回 NaN。
- **修复**：`const raw = String(value ?? "").trim(); if (!raw) return fallback;` 再做数字判断。
- **状态**：已确认（`Number("") === 0` 是 JS 语义）。

#### BUG-5 设置页没有监听存储变更，会静默覆盖弹窗的修改

- **位置**：`options.js`（全文件 `storage.onChanged` 出现 **0 次**）
- **对比**：`popup.js` 有 1 处，`timezone.js` 有 1 处。
- **影响**：设置页和工具栏弹窗同时打开时，在弹窗里改了开关（如聊天翻译总开关），再回到设置页点「保存设置」——设置页会用**它打开时读到的旧值**整体写回，把弹窗的修改无声覆盖。用户看到的是"设置保存成功"，但实际被改回去了。
- **修复**：设置页监听 `storage.onChanged` 同步界面；或保存时只写用户实际改动过的字段。
- **状态**：已确认（grep 计数为 0）。

### 中等（特定场景下出错或浪费）

#### BUG-6 批量翻译里模型返回数字 id 会导致整批作废（v3.9.12 已修）

- **位置**：`background.js` `parseBatchTranslationOutput()`
- **问题**：`if (... || typeof row.id !== "string" || ...) throw new Error("批量翻译包含无效项目")`。
- **影响**：提示词虽然要求 `[{"id":"0","text":"..."}]`，但模型经常把 `"id": 0` 回成数字。一旦如此，**整批**被判无效 → 走降级路径按每 4 条一组重试 → 12 条消息从 1 次请求变成 3 次，16 条变成 4 次。白花钱且明显变慢。
- **修复**：`String(row.id)` 归一后再比对，不要因为类型就判整批死刑。
- **状态**：已确认。

#### BUG-7 批量里单条失败被静默丢弃，且不说明原因

- **位置**：`background.js` `translateGoogleFreeBatch()`、`translateItemsIndividually()`
- **问题**：失败项返回 `{ text: "" }`，随后被 `.filter(item => item.text)` 移除；逐条重试路径还用 `catch (_)` 吞掉异常对象。
- **影响**：消息上会显示红色失败标记（`markMessageProgressFailed`），所以用户知道"这条没成功"，但**完全不知道原因** —— 是限流？内容被安全策略拦截？还是超时？三类问题的处理方式完全不同，用户只能瞎试。
- **修复**：把 `error.message` 一并回传，在失败提示里说明原因。
- **状态**：已确认（红色标记这点比原报告描述的要轻，已修正）。

#### BUG-8 自动归一改写了什么，用户看不到（v3.9.13 已随功能移除）

- **位置**：`background.js` `finalize()` / `withWarnings()`（两个函数都已在 v3.9.13 删除）
- **问题**：`finalizeTranslation` 会返回 `changes`（记录了把哪些写法改成了什么），但解构时只取 `text` 和 `warnings`，批量出口也只透传 `id/text/warnings`。
- **影响**：开启「自动统一柜型写法」后，译文被静默改写，用户无从核对。这与该功能"让客户看到的和报价单一致"的设计意图相悖 —— 用户恰恰需要看到改了哪里才敢放心。
- **修复**：透传 `changes` 并在译文旁给一个可查看的提示。
- **状态**：**已关闭** —— v3.9.13 把「自动统一柜型写法」整体移除，`changes` 与 `warnings` 两个字段一起消失，问题不再存在。

#### BUG-9 联系人标题读不到时，号码与语言缓存会串台

- **位置**：`timezone.js` `getContactTitle()` / `getPhone()` / `resolveContactFacts()`
- **问题**：`getContactTitle` 的兜底返回值是固定串 `"当前联系人"`。而 `getPhone` 的缓存键是 `title`，`resolveContactFacts` 的 `languageKey = phone || title`。
- **影响**：任何两个"标题暂时读不到"的联系人（切换会话的瞬间、WhatsApp 改版导致选择器失效时）都会共用同一个缓存键 → 第二个联系人直接显示第一个的**号码、归属地、当地时间、语言**。这类错误用户很难联想到原因。
- **修复**：标题为空时改用会话级唯一标识（或用 `phone` 兜底），并在标题不可靠时禁止写缓存。
- **状态**：已确认（兜底串就在代码里）。

#### BUG-10 同名联系人共用号码扫描缓存

- **位置**：`timezone.js` `getPhone()`：`phoneScanKey = found ? title : ""`
- **影响**：两个备注名相同的联系人（外贸场景常见：同一公司多个采购）会共用同一个号码。
- **修复**：缓存键加入会话标识，不要只用标题。
- **状态**：已确认。

#### BUG-11 号码可能从左侧列表里"别人的那一行"抓到

- **位置**：`timezone.js` `findPhoneInVisibleContactPanel()`
- **问题**：筛选条件是"位于右半屏 + 文本含 ≥7 位数字"，没有限定"当前打开的会话所在行"。
- **影响**：可能抓到联系人列表中其它行的号码 → 归属地、当地时间、语言全部跟着错。
- **修复**：只从高亮/激活的会话行提取。
- **状态**：已确认（筛选逻辑如描述）。

#### BUG-12 存储监听没有键过滤，无关写入也会触发全量更新

- **位置**：`timezone.js` 的 `chrome.storage.onChanged` 监听
- **对比**：`content.js` 有 `WATCHED_KEYS` 白名单，`timezone.js` 这边**任何 local 键变化**都 `scheduleUpdate(0)`。
- **影响**：后台写 `providerModelCache`、`contactSessionKey` 等键时，会触发每个打开的标签页做一次全量更新（读配置 + 联系人解析 + 重渲染）。
- **修复**：照搬 `WATCHED_KEYS` 过滤。
- **状态**：已确认。

#### BUG-13 每次更新都重算语言识别（含强制布局）

- **位置**：`timezone.js` `resolveContactFacts()`
- **问题**：每次 `update()` 都无条件执行 `getRecentIncomingMessages()`（对候选节点做 `getBoundingClientRect` → 强制同步布局）和 `detectCustomerLanguage()`（franc 统计识别），没有先判断"联系人或消息是否真的变了"。
- **影响**：WhatsApp 的 DOM 抖动很频繁（正在输入、时间戳刷新、消息渲染），每次都会带一次强制布局 + 一轮语言识别。
- **修复**：用"标题 + 最近消息指纹"做短路判断。
- **状态**：已确认。

#### BUG-14 硬信息校验的**误报**（已实测，比预期严重）（v3.9.13 已随功能移除）

- **位置**：`verify.js`（该文件已在 v3.9.13 整体删除）
- **实测结果**（直接执行 `TLP_VERIFY.verifyTranslation`）：

| 输入原文 | 译文 | 实测结果 |
| --- | --- | --- |
| `元旦快乐` | Happy New Year | ❌ 误报「译文里没有出现货币单位（原文为 CNY）」 |
| `这是一个单元` | one unit | ❌ 误报「…原文为 CNY」 |
| `元气满满` | （任意） | ❌ 误报「…原文为 CNY」 |
| `元宵节快乐` | （任意） | ❌ 误报「…原文为 CNY」 |
| `try again please` | （任意中文） | ❌ 误报「…原文为 TRY」 |
| `长20尺` | 20 feet long | ❌ 误报「柜型 20GP 在译文里丢失」 |
| `高40尺` | 40 feet high | ❌ 误报「柜型 40GP 在译文里丢失」 |
| `ISO 9001` ↔ `ISO9001` | 双向 | ❌ 两个方向都误报「型号丢失 / 多出」 |
| `PI2026 请确认` | Please confirm PI 2026 | ❌ 误报「型号 PI2026 丢失」 |
| `TT30天` | TT 30 days | ❌ 误报「型号 TT30 丢失」 |

- **根因**（三条独立缺陷）：
  1. **`元` 没有词边界**：`元` 作为货币单位用子串匹配，于是「元旦」「单元」「元气」「元宵」全部命中 CNY。这是**最高频**的一条 —— 元旦祝福是客户会发的。
  2. **`TRY` 是真实英文单词**：作为土耳其里拉代码被无差别匹配，「try again」这类句子必中。
  3. **型号正则不允许字母与数字之间有空格**：`([A-Z]{2,8})[-/]?(\d{2,6})`，所以 `ISO 9001` 与 `ISO9001` 对不上。`NON_MODEL_PREFIXES` 也缺 `PI`、`TT` 这类外贸高频缩写。
- **影响**：**误报比漏报危险得多** —— 它训练用户忽略这个提示。等到真的出现柜型写错、价格数字丢失时，用户已经不看警告了。
- **修复**：
  - `元` 改用词边界或要求前面是数字/货币语境（`\d\s*元` 或排除「元旦/单元/元宵」这类词）。
  - `TRY` 要求大写或前后有数字（`TRY\s*\d` 或 `\d\s*TRY`）。
  - 型号正则允许可选空格，但**要小心**：直接放开会引入新的误报（如 `TT 30`），需要同时扩充 `NON_MODEL_PREFIXES`。
- **状态**：**已实测确认**（上面每一行都是真实执行结果），**但已在 v3.9.13 随功能整体移除而关闭**。
  保留这条记录的理由是它本身是一份教训：一个"只提示、不修改"的功能，
  误报的代价是**让用户学会忽略所有提示** —— 这比不做这个功能更糟。

#### BUG-15 `busy` 标志在 try 之外赋值，异常时功能静默失效（v3.9.12 已修）

- **位置**：`content.js` `translate()`：`busy = true; showSpinner(field);` 写在 `try` **之前**。
- **影响**：`showSpinner` 一旦抛异常，`finally` 不会执行，`busy` 永久为 `true` —— 之后每次触发都只提示"上一条还在翻译中"，输入框翻译彻底失效，且只能刷新页面恢复。
- **概率**：低（`showSpinner` 内部已对 `getBoundingClientRect` 做了 try/catch）。但修复成本是**一行**，收益是消除一个"只能刷新页面"的故障模式。
- **修复**：把 `showSpinner` 移进 `try`。
- **状态**：已确认。

## 三、UI 问题

### UI-1 深色模式基本没有适配（最值得修的一条）

| 位置 | 问题 |
| --- | --- |
| `timezone.css` | 标签文字用 `--wat-text: #111b21`（近黑），**直接叠在 WhatsApp 深色标题栏上** → 几乎不可见。`timezone.js` 里**没有任何**深色检测代码 |
| `timezone.css` | 弹层背景 `--wat-popover-bg: #ffffff` 硬编码（JS 从不改它），内部 `#667781`/`#f0f4f2`/`#edf1ef` 全部写死 → 深色模式下弹层恒为纯白，与页面割裂 |
| `options.css:2`、`popup.css:1` | 都设了 `color-scheme: light`，没有 `prefers-color-scheme` 分支 → 系统深色下设置页和弹窗强制浅色，原生控件（下拉框、滚动条）也被锁成浅色 |

> 说明：`timezone.css` 里唯一的深色媒体查询只覆盖了译文警告条（`.tlp-chat-translation-warning`）。

### UI-2 强调绿硬编码了 4 种不同色值

`options.css` 里同时出现 `#008069`、`#087761`、`#08765f`、`#005f4d` —— 版本徽章、滑杆数值、成功提示、按钮取色不统一。视觉上"差一点点"，说不清哪里不对，但整体显得不精致。**建议抽成 3 个 CSS 变量**（主色 / 深色态 / 浅色态）。

### UI-3 响应式断点偏小

`options.css` 的断点是 **760px**，但两栏布局（`1fr + 360px` / `1fr + 320px`）在 761–900px 区间仍然生效 → 左栏被压到约 380px，微调输入框和长标签挤在一起。**建议把断点提到 900px**（代码里其实已经有 900px 的先例）。

### UI-4 同一个开关在两个地方叫不同名字

`options.html` 叫「允许快捷键」，`popup.html` 叫「允许聊天翻译快捷键」，实际控制的是**聊天翻译总开关**（`timezone.js` 用它决定是否响应快捷键）。名字既不统一、也没说清它到底控制什么。

### UI-5 可访问性

| 位置 | 问题 |
| --- | --- |
| `options.css` / `popup.css` | 开关的原生 input 用 `opacity: 0; position: absolute` 隐藏，`.toggle` / `.switch` 没有 `:focus-within` 样式 → **Tab 聚焦到开关时没有任何可见焦点**，键盘用户不知道自己在哪 |
| `popup.html` | 有一个 `<label class="switch">` 里只有 checkbox 和一个空 `<span>`，既无文字也无 `aria-label` → 屏幕阅读器读不出这个开关是干什么的 |
| `options.css` | 11px 小字对比度不足：作者署名 `#86938d` ≈ 2.6:1、字段说明 `#839098` ≈ 3.0:1，均低于 WCAG AA 的 4.5:1 |
