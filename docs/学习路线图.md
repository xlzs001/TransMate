# TransMate 团队技术能力提升路线图

> 这份路线图不是"推荐你学什么"，而是"**拿这个项目里的哪个函数，练哪个能力**"。
> 每周的任务都能在现有代码上完成，不需要另找练手项目。

---

## 一、先看清现在在哪

| 能力层 | 表现 | 你们现在 |
| --- | --- | --- |
| **L0 能跑** | 改完刷新扩展，手动点一遍，看起来没问题就发布 | 起点 |
| **L1 有工具** | 改之前先写测试；提交前跑门禁；改动有版本可回滚 | 本轮已铺好地基 |
| **L2 会设计** | 知道什么时候拆函数、什么时候该用数据表；边界条件成习惯 | 目标 |
| **L3 会判断** | 知道什么时候**不**写代码；敢删代码 | 长期 |

**关键认知：L0 → L1 不是靠"更小心"，是靠"有工具"。**
人一定会犯错，所以要让机器在提交时拦住错误，而不是靠人记住。
本轮已经把 L1 的工具全铺好了 —— 现在缺的是**用它**。

---

## 二、第 0 步：把工具用起来（本周就做）

不需要学任何新知识，只需要改掉一个习惯。

### 2.1 装一次

```bash
npm install      # 装开发依赖（eslint / acorn），只需一次
npm run check    # 跑全部门禁，约 2.4 秒
```

### 2.2 然后记住一条

> **改任何代码，提交前跑 `npm run check`。红了就修，修不了就问。**

这一条做到了，团队的 bug 率立刻下降一大截 ——
因为现在门禁覆盖的 8 类问题，以前全靠人眼。

### 2.3 用一个真实例子体会门禁的价值

初版基线那一轮，「默认值一致性」门禁第一次运行时，抓到了这个
（**这是历史输出，行号以当时为准**）：

```
timezone.js:DISPLAY_DEFAULTS 第 3258 行：provider 默认值 "gemini" 与 DEFAULTS 的 "" 不一致
```

这个 bug 的后果：新装用户在内容脚本侧被当成"已选 Gemini"，
而设置页和后台解析成免费档。**三处行为不一致，且不报错**，只偶尔走错服务商。
以前这种问题只能等用户反馈"翻译有时候不对"，然后花几小时排查。

门禁花了 0.09 秒就找出来了。**这就是工具的意义。**

## 三、12 周计划

每周 2 ~ 3 小时。每周都有明确产出，不是"看书"。

### 阶段 A：会读代码（第 1 ~ 2 周）

**目标**：能看懂一个 800 行的文件，说出它分几块、每块干什么。

| 周 | 任务 | 产出 |
| --- | --- | --- |
| 1 | 读 `background.js`（887 行），画出"消息进来 → 分流 → 翻译 → 返回"的流程图 | 一张手画流程图 |
| 2 | 读 `timezone.js` 的聊天翻译队列段（`pumpChatTranslationQueue` 一带），用自己的话写出"为什么一批最多 12 条、同一批为什么必须同目标语言" | 一段 200 字的说明 |

**自检**：能不能不看代码，说出 `background.js` 里 `callProvider` 支持的 6 种服务商分别走什么路径？

> 读代码比写代码重要，但没人教。**先读透一个文件，胜过写十个新功能。**

### 阶段 B：会补测试（第 3 ~ 4 周）

**目标**：能给一个现有函数补上测试，且测试真的能抓到错误。

| 周 | 任务 | 产出 |
| --- | --- | --- |
| 3 | 照抄 `temp/regression-checks.cjs` 里的 `scriptDetectModule()`，给 `providers.js` 的预设表写 3 条测试 | 3 条通过的测试 |
| 4 | 给 `timezone.js` 的 `normalizePhone` 补 5 条边界测试（空串、纯符号、超长、带国家码、纯本地号） | 5 条通过的测试 |

**怎么算"真的能抓到错误"** —— 现在有工具了，直接跑：

```bash
npm run test:mutation
```

它会故意把代码改坏，看你的测试会不会红。如果某个变异显示 `[漏掉]`，
说明那块逻辑没有被任何用例覆盖。想单独验自己的测试，可以照着
`temp/mutation-test.cjs` 里的写法加一条变异点，再跑一次。

手工验证也行：把你写的测试里的期望值故意改错一个，确认测试变红，再改回来。
**不会变红的测试等于没写。**

> 这一步的收获最大。写测试会逼你回答"这个函数到底应该输出什么"，
> 很多设计问题在写测试的时候就暴露了。

### 阶段 C：会拆函数（第 5 ~ 7 周）

**目标**：能把一个 60 行的函数拆成 3 个 20 行的，且行为完全不变。

**练习对象**（按难度排序）：

| 顺序 | 位置 | 现状 | 拆法提示 |
| --- | --- | --- | --- |
| 1 | `options.js:376` `loadSettings` | 62 行 / 复杂度 24 | 按"读存储 / 校验 / 填表单"拆三段 |
| 2 | `timezone.js:3723` `getRecentIncomingMessages` | 45 行 / 复杂度 22 | 按"取候选节点 / 过滤 / 截断"拆三段 |
| 3 | `timezone.js:3961` `pumpChatTranslationQueue` | 56 行 / 复杂度 24 | 按"取待翻译 / 请求 / 回填"拆三段 |

**已经拆好的三个，可以当参考答案读**（都在 git 历史里）：

| 位置 | 改前 → 改后 |
| --- | --- |
| `popup.js` `render` | 41 行 / 复杂度 31 → 5 行调用 + 5 个分区函数 |
| `timezone.js` `update` | 94 行 / 复杂度 32 → 编排 + 5 个函数 |
| `background.js` `translateChatBatch` | 115 行 / 复杂度 22 → 47 行 / 8 |

用 `git log --oneline` 找到对应的提交，再看 `git show <提交>` 逐行读 ——
**读别人的重构 diff，比读重构后的成品收获大得多**，因为你能看到"从哪一步开始变好的"。

**铁律（顺序不能反）**：

```
1. 先补测试，跑到全绿
2. 再拆
3. 拆完测试还是全绿 → 说明行为没变
```

反过来做（先拆再补测试）就是"换一种方式犯错"——
你不知道自己是拆对了，还是把一个 bug 拆成了两个。

**自检**：拆完之后，`npm run metrics` 里那个函数的复杂度和行数都降了，
而 `npm run check` 还是全绿。另外别忘了去 `temp/quality-budget.cjs` 删掉对应的名单条目 ——
不删的话质量预算门禁会直接拦住你（这是设计好的，见手册 5.3）。

### 阶段 D：会设计（第 8 ~ 10 周）

**目标**：学会辨认"伪装成代码的数据"，并把它们还原成数据。

**先读这个真实案例**（`timezone.js` `detectSingleLanguage`，本轮已重构）：

```js
// 改之前：20 多个分支，复杂度 42
if (/[\u3040-\u30ff]/.test(text)) return makeDetectedLanguage("jpn", 1);
if (/[\uac00-\ud7af]/.test(text)) return makeDetectedLanguage("kor", 1);
// ...

// 改之后：表 + 8 行循环，复杂度 10
var SCRIPT_LANGUAGES = [
  [/[\u3040-\u30ff]/, () => ["jpn", 1]],
  [/[\uac00-\ud7af]/, () => ["kor", 1]],
  // ...
];
```

**练习**：找一处你自己写的、`if` 分支超过 5 个的地方，问自己：

> 这些分支里，有没有一个分支是"因为另一个分支的存在而存在"的？

如果没有 —— 每个分支都是独立地"匹配 → 返回常量" —— 那它就是数据。
改成表，并保证**顺序不变**，然后补测试钉死顺序。

**再看一个更难的形态**：一堆分支的代码**完全一样**，只是操作的数据不同。

上一节的表是"分支只差常量"，这种好认。真正难的是：六段循环写法一模一样，
只差三个东西 —— 读哪个字段、报什么 `kind`、怎么判断"它在文本里"。
改一次措辞要同步改六处，漏一处就是文案不一致，而且没有任何东西会提醒你。

改法同样是"抽成一张表 + 一个循环"，**但真正要学的是"表在哪里停下"**：

- 有一类值允许在译文里换个写法表达（比如数字写成中文"六层"），
  它的"丢失"和"多出"两个方向规则**不对称** —— 一个方向要先折算别名，
  另一个方向只看规范形式，否则常用词会凭空造出值来。
- 还有一类是符号有多义，判定标准要从"完全相等"放宽成"两边存在共同候选"。

这两种都**不该**塞进表里 —— 硬凑进去就得写 `if (kind === 'number') ...`，
比原来的六段循环更难懂。

> **只有当分支之间"只差数据"时才合并。**
> 一旦发现要往表里加特判，就说明它不属于这张表。
>
> **强行统一是比重复更糟的毛病**：重复至少还能一眼看出两处不一样，
> 硬凑出来的抽象会把差异藏进 `if` 里。

完整对照（含一个已被移除模块的原始形状）见手册 5.2。

**自检**：改完之后，"加一种新情况"的操作从"改控制流"变成了"加一行"，
而且**没有引入任何 `if (kind === ...)` 之类的特判**。

### 阶段 E：会处理边界（第 11 ~ 12 周）

**目标**：写任何函数时，自动想到"如果传进来的是空/超长/并发怎么办"。

**检查清单**（每次写函数都过一遍）：

- 传 `null` / `undefined` / `""` 会怎样？
- 传超长文本（10000 字）会怎样？有没有做长度上限？
- 网络失败 / 超时 / 返回非 JSON 会怎样？
- 同一个操作被快速触发两次会怎样？（本项目的 `translateChatBatch` 有并发保护）
- 上游返回了意料之外的格式，会静默出错还是明确报错？

**练习**：给 `timezone.js` 的 `normalizePhone` 找 3 个"可能出问题但没处理"的输入。
（提示：号码里混进分机号怎么办？同一段文字里出现两个号码取哪个？
带 `+` 与不带 `+` 的写法算不算同一个号？）

**加练**：本项目修过的一类边界是**顺序敏感**的 —— 聊天批量翻译会把待翻译消息
攒成一批再发，而攒批时规定了"最多 12 条、总字符不超过 14e3，
且同一批必须同目标语言、同一次会话"。所以"谁和谁分在一批"是有语义的。
这类"顺序即语义"的地方必须补测试钉死，否则某次重构调换了分组条件，
没有任何东西会报错 —— 只是偶尔翻译结果串到别的语言上。

## 四、团队层面：怎么让这件事持续下去

个人练完就散了，是大多数团队技术提升失败的原因。需要机制。

### 4.1 每周 30 分钟代码评审会

- 挑一个本周的改动，投影出来逐行过
- **只讲两件事**：这次改动为什么这么做；有没有更好的做法
- 不讲对错，只讲取舍。评审的目标是让所有人学会判断，不是找责任人

### 4.2 轮值

每周换一个人负责"门禁守护"：
- 确认 CI 是绿的
- 有人卡住了帮他一起看
- 记录本周门禁抓到的真问题（积累成团队的"坑清单"）

### 4.3 把踩过的坑写进规范

每踩一个新坑，就往 `docs/工程规范手册.md` 加一条。
**规范手册应该是长出来的，不是一次性写出来的。**

### 4.4 度量只看趋势，不做考核

`npm run metrics` 的数字**绝对不能**用来考核个人。

一旦用来考核，所有人都会把代码写得"指标好看"而不是"容易维护"——
比如把一个 100 行的函数拆成 10 个互相调用的 10 行函数，
复杂度好看了，可读性反而更差。

度量是用来**发现哪里值得看一眼**的，不是用来打分的。

**一个具体的例子**：`popup.js` 的重构做完之后，文件从 135 行涨到 158 行。
如果按"代码行数"考核，做这件事的人不及格 —— 但他的代码明显更好了。

> **看分布，不看总量。** 最长函数降了、最复杂函数降了、超标的函数少了，
> 这才是"变好"；总行数涨了很正常，因为拆函数本身要写更多行。

### 4.5 例外清单必须自带"什么时候删掉我"

`temp/quality-budget.cjs` 里有一份"暂时接受"的清单（当前 4 条）。
它之所以不会烂掉，是因为门禁有一条 R3 规则：**条目一旦达标就要求删掉**。

这条规则值得抄到任何团队。**任何一份"暂时接受的例外清单"，
都必须自带一条"什么时候该删掉我"的规则**，否则它一定会变成永久豁免。

## 五、推荐资源（少而精）

不要贪多。下面这几个看完，比刷十个教程有用。

| 类型 | 名称 | 为什么推荐 |
| --- | --- | --- |
| 书 | 《重构：改善既有代码的设计》Martin Fowler | 第 6 章"第一组重构"最实用；不用通读，当手册查 |
| 书 | 《代码大全》第 2 版 | 只读第 7 章（高质量的子程序）和第 8 章（防御式编程） |
| 书 | 《修改代码的艺术》Michael Feathers | 讲"怎么给没有测试的代码补测试"，正是本项目的处境 |
| 文档 | ESLint 规则列表 | 不需要背，但每次门禁报错时去看一眼那条规则为什么存在 |
| 实践 | 本项目的 `docs/代码质量基线报告.md` | 所有概念都能在这里找到真实例子 |
| 实践 | `git log` 里的三次重构提交 | 读 diff 比读成品有用：能看到"从哪一步开始变好的" |

**不建议**现在去学 TypeScript / 框架 / 架构模式。
本项目 4074 行自有代码，用不上那些。
**先把"会读、会测、会拆"练熟，这三样能解决 80% 的问题。**

## 六、三个月后怎么判断有没有进步

不要看"学了多少"，看这几件事能不能做到：

- [ ] 改代码前，会先问"我怎么知道改对了"
- [ ] 提交前会跑 `npm run check`，看到红的会自己修
- [ ] 能对一个 60 行的函数说出"应该拆成哪几段"
- [ ] 能辨认出"伪装成代码的数据表"
- [ ] 能说出"这张表在哪里该停下"，而不是把什么都硬塞进表里
- [ ] 写断言时会问"这是不变量还是当前写法"（不会去数调用次数）
- [ ] 看到 `catch (_) {}` 会主动补上为什么
- [ ] 加新设置时，知道要同步 5 个地方（或者知道让门禁帮你查）
- [ ] 代码评审时，能说出"这里我倾向 A，因为……"而不是"我觉得 A 好"

全部打勾，团队就从 L1 到 L2 了。
