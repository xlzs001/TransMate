# TransMate v3.7.2：代码检查与 AI 润色建议

> **版本说明**：本文记录 **v3.7.2 时点**的审查结论与建议，其中一部分已在后续版本（v3.9.x）处理，
> 保留作为工程过程记录 —— **不代表当前代码状态**。当前状态见
> [`功能与问题盘点.md`](功能与问题盘点.md)。

## 结论

存在需要修复的逻辑问题，优先处理“翻译结果覆盖后续编辑”“截断结果当成功回写”“富文本多行写入误报”。建议先解决写入安全，再增加“按需译后润色 + 预览采用 + 恢复原译文”。

现有程序已经提供“意译润色专家”：`options.js:73` 的 `paraphrase` 对应 `background.js:232–235` 的翻译提示词。这属于翻译过程中的表达优化，不是独立的译后二次润色。

### 检查范围与可信度

- 对扩展入口、输入框翻译、服务适配、设置页、聊天翻译队列以及时区相关业务代码进行了只读审查。
- 对 `background.js`、`content.js`、`options.js`、`popup.js`、`providers.js`、`timezone.js` 执行了 `node --check`，全部通过。语法通过不代表业务行为正确。
- 使用当前源码在 Node 隔离环境中模拟浏览器接口、网络响应和输入框，复现了 **8 个异常场景，归为下文 7 类已复现问题**。模拟断言全部通过，表示异常行为得到确认，不是表示业务验收通过。
- 补充记录 1 项静态确认的状态不一致问题。
- 未使用真实 API Key，未发送客户文本，未调用实际翻译服务，未更改浏览器设置或扩展业务源码。仅新增本报告及本地审查脚本 `temp/audit-checks.cjs`。
- 未进行真实浏览器端到端测试、所有网页兼容性测试或第三方接口可用性测试；不能据此承诺没有其他 BUG。

## 一、已复现问题

### B1 高优先级：翻译等待期间继续输入，新内容会被旧译文覆盖

**位置：** `content.js:417–445`，以及实际写入函数 `399–410`。

**根因：** 发请求前读取 `source`，响应回来后直接调用 `writeField(field, output)`。期间没有检查输入内容版本、目标是否仍属于原会话，也没有核对用户是否已经编辑。`busy` 仅阻止另一次翻译，不阻止输入框继续被编辑。

**复现：** 让翻译请求暂不返回；用户修改字段；再返回旧原文的译文。模拟结果显示新输入被覆盖。

**影响：** 草稿丢失。对于复用输入框节点的单页聊天页面，还存在切换会话后写错上下文的风险；该跨会话风险尚未在真实页面验证。

**建议：**
- 发请求时记录字段、原始文本、输入版本、会话标识与请求编号。
- 写入前重新检查；发生编辑、字段断开、会话切换或请求过期时，改为展示结果，不能强制覆盖。
- 写入函数存在异步等待和多级兜底，检查应覆盖实际替换点，不只在函数外检查一次。
- 原文保存在当前字段的短期状态中，支持恢复；恢复前同样保护后续手动编辑。

### B2 高优先级：输出截断也被当成成功，可能替换为不完整译文

**位置：** `background.js:107–194`、`343–362`；`content.js:440–445`。

**根因：** 输入框翻译未传入输出预算，使用 `maxOutputTokens = 800` 默认值；各生成式适配分支主要提取文本，未把结束原因反馈给调用方。非空文本就会作为成功结果返回并回写。

**复现：** 模拟接口返回非空文字，结束原因明确为 `finish_reason: "length"`。消息处理器仍返回 `ok: true`；实际请求预算为 800。

**影响：** 长邮件、报价说明或技术描述在服务端触发输出上限时，可能只留下半截译文。不能把某个固定中文字数当成必然截断阈值，实际取决于目标语言、服务和文本。

**建议：**
- 适配层返回结构化结果，例如文本、结束原因、是否完整，而不是只返回字符串。
- 按服务协议识别长度截断、空响应及异常结束；不完整结果不得自动覆盖原文。
- 按输入规模和服务能力设置输出预算；长文本按语义段落处理并检查结果完整性，而不是仅提高一个固定数字。
- 批量路径也应有完整性检查；当前按消息数量估算预算，并不能覆盖少量超长消息。

### B3 中优先级：富文本已成功写入，但提示“页面阻止了自动写入”

**位置：** `content.js:53–60`、`205–207`、`281`、`310`、`338`。

**根因：** `readField(field)` 保留内部换行和连续空格，而比较右侧的 `normalize(text)` 把这些折叠成单个空格。三条富文本回写路径的判定口径不一致。

**复现：** 模拟成功插入两行文本，字段内容与目标完全相同，但 `insertViaExecCommand()` 返回 `false`。

**影响：** 包含换行或连续空格、且页面保留该格式时，可能重复进入粘贴和 DOM 兜底，最终误报失败。单行普通文本不一定触发。

**建议：** 最小修正是两侧采用同一归一化方式：

```js
normalize(readField(field)) === normalize(text)
```

但上述宽松比较不能保证段落格式保留。若换行属于验收要求，应另做格式检查，避免把“换行被折叠”误判为完全成功。

### B4 中优先级：获取服务配置列表期间切换服务，结果串到另一服务

**位置：** `options.js:303–333`、`389–392`，尤其 `320–323`。

**根因：** 请求使用最初的 `payload`，但返回后用可变的全局 `activeProvider` 写缓存和渲染。获取期间禁用的是操作按钮，没有冻结服务选择。

**复现：** 向服务 A 发出列表请求，等待时切换到服务 B，再让 A 的响应返回。列表被写入 B 的缓存并展示到当前下拉框。

**影响：** 用户可能为服务 B 选到服务 A 的配置项，后续请求失败或选项混乱。

**建议：** 请求开始时捕获服务 ID 与请求版本。缓存写回原服务；仅当当前服务及请求版本仍匹配时更新界面。旧请求的 `finally` 也不应覆盖新请求的按钮状态。

### B5 中优先级：批量响应只校验能否解析，缺少结果结构与覆盖率校验

**位置：** `background.js:403–420`、`489–517`；`timezone.js:3949–3956`。

本类包含两个已复现场景：

1. 输入两条消息，模拟返回合法 JSON 但只有第一条。后台只返回一条结果，不对缺失项做兜底。前台会将缺失项标记失败，因此不是前台静默成功，但后台恢复逻辑没有补齐。
2. 响应的 `text` 为对象时，`String(row?.text || "")` 将其转换为 `[object Object]` 并接受，后续可能把这段无效文字展示成译文。

**建议：**
- 校验每项为对象，`id` 属于本次请求，`text` 为非空字符串；拒绝重复 ID、未知 ID 和错误类型。
- 对缺失或无效项单独重试，保留已经有效的结果，不整批重译。
- 区分格式错误、超时、限流、权限错误。限流需退避，权限错误应停止；不能把所有网络错误都拆成更多单条请求，否则会放大负担。
- 当前网络失败不进入 JSON 解析兜底，是恢复策略限制，不应把每一次外部网络故障都归类为代码 BUG。

### B6 中低优先级：未填接口地址阻塞无关设置保存

**位置：** `options.js:288–295`、`514–554`；空地址预设见 `providers.js:74–80`、`100–105`。

**根因：** “保存设置”首先对当前服务地址校验并请求权限，然后才保存所有设置。因此，尚未填地址的服务草稿会连带阻止外观、开关、快捷键等配置保存。

**复现：** 当前服务地址为空，触发原保存处理函数，得到“保存失败：API 地址格式不正确”，未调用设置写入。

**判定边界：** 拒绝无效接口地址本身合理；问题是服务配置校验与所有基础设置强耦合。这属于可用性缺陷，不是地址校验器错误。

**建议：** 基础设置与服务配置拆分保存，或允许保存未完成草稿并明确标注不可用；不要默默激活错误服务。真正调用服务前仍须检查地址、凭据与权限。

### B7 低优先级：连按空格计数跨输入框累计

**位置：** `content.js:47–49`、`465–497`。

**根因：** `spaceCount`、`lastSpaceAt` 为文档级变量，没有绑定字段，也没有在焦点变更时清零。

**复现：** 在字段 A 按两次空格，然后在超时前用鼠标切到字段 B 按一次空格，触发了字段 B 翻译。使用 Tab 切换可能因非空格按键重置而不触发，因此不是所有切换方式都会复现。

**建议：** 记录上次触发字段，字段变化或失焦时重置；忽略按键自动重复，并明确是否允许带修饰键的空格触发。

## 二、静态确认的问题及未验证边界

### S1 已识别号码，但缺少地区信息时，状态丢失号码

**位置：** `timezone.js:4535–4543`、`4645–4653`；相关保存逻辑 `4429–4436`。

当存在 `phone`，但无法获取地区或时区时，调用 `renderUnknown()` 将 `activeState.phone` 设为 `null`；随后仅把号码写到 DOM，再发布仍为空的状态。于是页面可显示号码，其他消费者收到的却没有号码，依赖 `activeState.phone` 的保存路径也直接返回。

建议区分“没有号码”与“号码已有但地区未知”两类状态，后者保留号码，同时如实标记地区、时区未知。本项基于明确赋值链静态确认，未模拟特定真实号码或页面。

### 未验证，不作为确定 BUG

- 预设服务中的配置项是否仍然可用，以及各生成服务是否接受当前请求参数，需要结合实际接口与账号验证。本轮没有远程验证，不推测某个名称不存在，也不声称某参数对全部服务失效。
- 第三方网页 DOM、受控编辑器、真实粘贴事件及浏览器权限行为仍需实机验证。
- 聊天缓存/失效指纹包含服务、配置项、语言和翻译风格，但未包含接口地址。更换接口但其他字段不变时，可能继续使用旧缓存；是否属于缺陷取决于产品是否要求换接口即重译。加入润色阶段时应一并规范缓存身份。

## 三、AI 润色功能：建议怎样做

### 1. 明确与已有功能的区别

| 路径 | 用途 | 建议 |
|---|---|---|
| 已有“意译润色专家” | 翻译时直接优化表达 | 保留；适合想要自然译文、不需要对比的场景 |
| 新增“润色译文” | 针对已翻译内容再次改写，可选择风格并比较 | 第一阶段推荐实现，默认手动触发 |
| 每次翻译后自动润色 | 无需再点击，但增加请求与等待 | 后续作为可选设置，不默认开启 |

独立二次处理并不保证质量必然更高；价值在于用户可以控制何时改写、按什么风格改写，以及是否采用。

### 2. 推荐第一版交互

1. 翻译完成后，在输入框附近提供“润色译文”，不占用现有连按空格动作。
2. 提供简洁风格：**自然表达、商务礼貌、简洁直接**。后续再考虑自定义指令。
3. 展示“原译文 / 润色后”预览，最好标出差异。
4. 提供“采用”“复制”“保留原译文”；只有点击采用才替换输入框，不自动发送消息。
5. 保留原文、原译文与采用前内容的短期快照，支持恢复；用户后来又编辑时，不直接覆盖恢复。

**范围建议：** 优先服务于用户准备发出的文本。收到的客户消息先以忠实理解为主，不默认再润色整屏聊天记录；否则容易改变语气、歧义或承诺强度，且产生重复请求。

### 3. 润色约束比风格数量更重要

润色请求建议同时携带：原文、当前译文、确定的目标语言、场景和润色风格。

- 数量、价格、币种、产品型号、尺寸、单位、交期、付款比例和贸易术语不能改变。
- 不新增折扣、承诺、库存、交付保证或催促理由。
- 保留否定、条件、可能性与语气强度，不能把“预计/可能”改成“保证”。
- 不自动增加称呼、落款、表情或原文没有的信息。
- 输入文本只当作待处理数据，不执行文本内部出现的指令。
- 保持目标语言，不重新套用自动翻译方向判断；否则英文译文可能又被转回中文。
- 本地对关键数字、币种、型号等做差异检查；发现变化时禁止自动采用并提示复核。该检查不能完全证明语义一致，仍需预览。

若只拿到用户粘贴的译文、没有原文，应明确这是“仅优化现有表述”，不能承诺与未知原文一致。

### 4. 失败与并发保护

- 润色失败时保留已成功的原译文，不丢弃、不替换成空内容。
- 空输出、截断结果、关键事实校验失败都不能自动采用。
- 结果回来时重新确认输入版本、会话和语言仍匹配；过期结果仅供预览。
- 翻译与润色使用独立操作类型，不要通过再次触发翻译快捷键实现润色。
- 新增阶段不要反复从全局设置读取目标语言或风格，使用发起本次任务时的配置快照。
- 默认只提交用户主动处理的文本，不追加整段聊天记录。若润色服务与翻译服务不同，应明确告知数据会发送给哪个服务。

## 四、代码接入建议

| 文件 | 建议改动 |
|---|---|
| `background.js` | 新增独立的 `TL_POLISH` 消息与 `polish()`；复用已有适配器、配置解析、超时/错误框架；返回结构化输出并校验结束状态 |
| `content.js` | 增加当前字段的原文/译文快照、请求版本、润色按钮和预览；先修复安全写入，再复用写入及复制逻辑 |
| `options.html` / `options.js` | 增加润色风格、默认关闭的自动润色选项；避免把润色风格与现有翻译专家配置混为同一个字段 |
| `providers.js` | 增加能力标记，区分当前适配器是否能按提示词进行润色；不能因有翻译能力就默认支持改写 |
| `popup.html` / `popup.js` | 可选：展示状态或快捷入口；不是首版必需 |
| `timezone.js` / `timezone.css` | 仅在后续支持消息气泡独立润色时扩展；首版不需要新建整套批量润色队列 |

当前专用翻译分支 `background.js:151–168` 没有执行传入的通用 `prompt`，因此不能简单复用它作为润色实现。应明确提示当前适配器不支持，或让用户选择支持改写的已配置服务；这不是对外部服务全部能力的断言。

建议消息字段包含 `requestId`、`sourceText`、`translatedText`、`targetLanguage`、`polishStyle`、`context`。提供商凭据由后台从配置读取，不放在页面预览中。

若引入缓存，其身份应至少区分：任务类型、服务及接口身份、目标语言、润色风格、原文、当前译文以及提示词版本。不要把明文 API Key 纳入缓存键，也不要把客户文本写进诊断日志。

## 五、落地顺序与验收

### 阶段一：先修复安全与正确性

- 修复 B1、B2、B3，确保旧结果不能覆盖新输入、不完整结果不能覆盖原文、多行写入不误报。
- 修复 B4 和 B5，避免服务配置串写及错误批量内容展示。
- 处理 B6、B7 和 S1，补充自动化回归用例。

### 阶段二：最小可用润色功能

- 手动“润色译文”、简洁风格选择、预览采用、复制及保留原译文。
- 目标语言固定，原文和译文同时提供；加入数字/型号等保护。
- 失败回退及输入版本保护必须与功能同时交付。

### 阶段三：按使用反馈扩展

- 可选自动润色、自定义风格、上下文范围控制。
- 若确有需求，再支持单条聊天消息润色与更完整的缓存机制；不先做整屏二次处理。

### 核心验收清单

- [ ] 多行和连续空格文本正确写入且无误报。
- [ ] 翻译/润色等待期间编辑内容，返回结果不得覆盖新编辑。
- [ ] 切换会话、字段失效或取消操作后，旧任务不能写回。
- [ ] 截断、空响应、错误 JSON 和不完整批次得到明确处理。
- [ ] 切换服务时，旧列表响应不污染新服务界面与缓存。
- [ ] 已翻译英文点击润色，仍保持指定目标语言。
- [ ] 数量、币种、型号、交期及否定条件不被改写；可疑变化提示复核。
- [ ] 润色失败仍可使用原译文；采用与恢复均不自动发送消息。

**最终建议：** 不必先大改架构或增加批量自动处理。先把“不会误写、不会丢内容”做稳，再做用户能比较、能选择、能恢复的译后润色。
