# TransMate 工程规范手册

> 写给每一个往这个仓库里写代码的人。
> 所有规则都来自本项目踩过的坑，不是从别处抄的。每条都尽量给出真实行号。

---

## 零、最重要的一条

**改代码之前，先确认改完你怎么知道它是对的。**

如果答不上来，就先写一个能失败的测试，再改。
这不是流程洁癖 —— 这个项目里已经有过两次"修好 A 弄坏 B"，
都是因为改的时候手上没有能立刻验证的手段。

## 一、提交前必做

```bash
npm run check      # 8 道门禁，约 2.4 秒
```

全绿才提交。这条命令跑的是：

| 门禁 | 防什么 |
| --- | --- |
| 静态检查（ESLint） | 拼错变量、恒真恒假、Promise 返回值写错 |
| 默认值一致性 | 5 份 DEFAULTS 副本漂移 |
| 回归测试（55 项） | 已修过的 bug 重新出现 |
| 审查项（8 项） | 版本号、HTML id、开关默认值不一致 |
| 中转服务冒烟（29 项） | 中转服务的请求/响应契约被改坏 |
| 空 catch 有说明 | 吞掉异常却不写为什么 |
| 质量预算 | 函数越写越长、越写越绕 —— 已经改好的地方再退回去 |
| 变异测试（10 个变异点） | 测试变成摆设 —— 代码改坏了，回归测试却还是绿的 |

**任何一道没过就不要提交。** 更不要用 `--no-verify` 之类的方式绕过 ——
门禁拦住你的那一次，通常正是你本来会漏掉的那个 bug。

后两道门禁的细节见 5.3 和第八节。单独跑某一道：

```bash
npm run test:budget      # 只看质量预算名单
npm run test:mutation    # 只跑变异测试
```

## 二、硬规则（门禁会拦）

### 2.1 不要裸用跨文件全局

`background.js` 里 `providers.js` 是用 `importScripts` 加载的，
它的全局挂在 `globalThis` 上。**必须带命名空间**：

```js
// 错：裸名，运行时 ReferenceError
const preset = PROVIDER_PRESETS[id];

// 对：带命名空间
const preset = TLP_PROVIDER_PRESETS[id];
```

`timezone.js` / `content.js` **根本没有加载 `providers.js`**。
所以在 `timezone.js` 里写 `TLP_PROVIDER_PRESETS` 是运行时错误 ——
表现为"某个按钮点了没反应"，在浏览器里极难定位。

这条已经被 ESLint 按文件声明锁住了（见 `eslint.config.mjs`），
写错了会直接报 `no-undef`。

> **反过来说：一个跨文件全局被删掉时，那条 `no-undef` 声明也必须跟着删。**
> v3.9.13 移除 `verify.js` 时漏了这一步的话，`eslint.config.mjs` 里
> `TLP_VERIFY: "readonly"` 会继续放行——以后谁写出这个引用，
> **静态检查不再报错，而运行时是 ReferenceError**。
> 门禁的"绿"是有前提的：它声明的那份全局清单必须和代码里真实存在的全局一致。

### 2.2 数字抽取的正则

从文本里抽数字**必须**用这个形状：

```js
/\d{1,3}(?:[,\u00a0 ]\d{3})+(?:\.\d+)?|\d+(?:\.\d+)?/g
```

**不要**写成 `/\d[\d,\s]*/`。后果是真实的：

```
输入：HR-2400, 20GP
错误正则读出：240020        ← 把两个数粘成了一个
正确正则读出：2400, 20     ← 两个数
```

外贸场景里数字错一位就是事故，而这类错误人眼扫一遍基本发现不了。

### 2.3 中文数字只在"丢失"方向还原

`六` → `6`、`三万` → `30000` 这种还原，**只在"原文有、译文没有"这个方向做**。

反方向（译文里的中文数字还原成阿拉伯数字）不能做，因为：

```
"我们一共出了 3 个柜"  →  "一" 被折成 1  →  凭空多出一个数字 1
"稍等一下"            →  "一" 被折成 1
"一直这样"            →  "一" 被折成 1
```

### 2.4 判定条件有包含关系时，先判更具体的

中文里"最后上线时间"**含有"上线"两个字**。所以判定"客户是不是当前在线"时，
顺序必须是：

```
1. 正在输入  →  2. 离线文案  →  3. 在线文案
```

先判在线，会把"最后上线时间"误判成"当前在线"。

**这条的通用教训**：当判定条件之间存在包含关系时，**先判更具体的**。

> 这个案例来自 v3.9.8–v3.9.10 的"客户在线状态指示灯"，该功能已在 v3.9.11 整体移除。
> 教训与功能无关，保留。

### 2.4.1 从外部页面抓信息：认不出就不要采用

实测踩到的坑：WhatsApp 用图标字体渲染图标，图标名（连字名）本身就是文本。
图标字体没加载时，页面上会原样显示一串 `ic-person-filled`。
当时"取状态行附近第一个有文字的元素"的实现，就把这串内部标识当成了客户状态。

正确做法是**白名单**：只有匹配得上已知文案才采用，否则一律当作"读不到"。

**通用教训**：从外部页面抓取信息时，**永远假设你会抓到不该抓的东西**。
默认应该是"不显示"，而不是"显示点什么" —— 宁可少显示，也不要显示错的。

这条与 2.4 是同一个取向：**先排掉已知的坏情况，再考虑采用**。

> 同上，案例来自已移除的在线状态指示灯；`timezone.js` 里仍在从 WhatsApp 页面
> 抓联系人标题、号码、语言（见 `resolveContactFacts`），这条规则继续适用。

### 2.4.2 删功能要连根删，半截状态最难维护

移除一个功能时，最容易留下的不是死代码，而是**半截状态**：

- 渲染删了、设置项还在 —— 用户勾了没反应；
- 设置项删了、存储键还在 —— 数据里躺着没人读的孤儿字段；
- 逻辑删了、样式还在 —— CSS 里留着没有使用者的类。

三种都不报错、不崩溃，只会慢慢腐烂。**判断标准：改完之后 `grep` 一遍功能名，
5 个源文件里应当一处都搜不到。**

本项目把这条做成了门禁：回归用例「已移除的功能不在界面与数据里留残骸」
会扫 `timezone.js` / `timezone.css` / `options.js` / `options.html` / `options.css`
五个文件，逐个检查被删功能的函数名、类名、存储键和界面文案是否全部消失。
**以后谁想"顺手补回一半"，提交时就会被拦下。**

### 2.5 空 catch 必须写清楚为什么可以吞

```js
// 错：半年后没人敢动这段代码
try { window.focus(); } catch (_) {}

// 对
try { window.focus(); } catch (_) { /* 非用户手势时浏览器会拒绝 */ }
```

说明可以写在 `catch` 前面，也可以写在块内第一行。门禁两头都认。

### 2.6 vendored 代码要用标记圈起来

`timezone.js` 里有 3230 行第三方打包产物（libphonenumber-js + franc）。
它必须用标记圈出来：

```js
/* eslint-disable */
// ===== 以下到第 3231 行是第三方库的打包产物，不要手改，升级时整段替换 =====
...
/* eslint-enable */
// 以下开始是本项目自己的代码
```

不圈起来的话，静态检查和度量都会把第三方代码算成"我们的问题"，
噪音会把真问题淹掉（本项目 3230 行噪音 vs 4062 行自有代码）。

### 2.7 加新设置要同时改 5 处

这是本项目最容易漏的地方。加一个 `watXxx` 设置，必须改：

| # | 文件 | 位置 | 作用 |
| --- | --- | --- | --- |
| 1 | `options.js` | `DEFAULTS` | **权威定义** |
| 2 | `options.js` | `APPEARANCE_DEFAULTS` 或 `CHAT_DEFAULTS` | 恢复默认时遍历用 |
| 3 | `popup.js` | `DEFAULTS` | 弹窗要读的部分 |
| 4 | `timezone.js` | `DISPLAY_DEFAULTS` | 内容脚本要读的部分 |
| 5 | `options.html` | 对应的 `id` | 设置页控件 |

漏掉第 4 处最危险：**不会报错**，只会静默用错默认值。

`npm run check` 里的「默认值一致性」门禁会检查这 5 处的子集关系和取值一致性。
本轮它第一次运行就抓到了 `provider` 默认值不一致。

### 2.8 自定义控件的样式：两个必踩的坑

用"隐藏原生控件 + 自己画一个"的方式做开关、勾选框时，有两个坑
**不报错、不警告，只能靠肉眼发现**。下面两条都实测踩过。

> 案例来自 v3.9.8–v3.9.10 弹层里的快捷开关（`.wat-toggle`），
> 该控件已在 v3.9.11 随在线状态指示灯一起移除。两条坑与具体控件无关，保留。

**坑一：选择器优先级 —— 隐藏的原生控件被通用规则撑大**

同一个面板里，文本框和下拉框通常共用一条规则：

```css
#wat-region-time-root input { height: 34px; padding: 9px; border: 1px solid ...; }
```

这条带 **ID 选择器**，优先级高于给自定义控件写的 `.my-toggle input`（只有类选择器）。
于是控件里那个 `opacity: 0` 的原生 checkbox 也被撑成 34px 高、加 1px 边框、9px 内边距。
视觉控件只有 18px 高，但**点到它下方 16px 也会切换** —— 用户会觉得"这个开关很飘"。

修法：给自定义控件的选择器也加上同样的 ID 前缀，让它的优先级不低于通用规则。

**规则**：写通用元素选择器（`input` / `select` / `button`）时，
先想清楚会不会误伤已有的自定义控件。**ID 选择器的优先级会静默盖掉类选择器**，
不报错、不警告，只能靠肉眼发现。

**坑二：外边距合并 —— 滑块被顶到轨道顶部**

滑块原来用 `margin: 2px` 定位：

```css
.my-toggle i::after { width: 14px; height: 14px; margin: 2px; }
```

`::after` 是**块级盒子**，它的上外边距会和父元素 `i` 发生
**外边距合并（margin collapsing）**，被一起推到轨道顶部。
结果滑块偏上、不居中，看起来像开关坏了。

修法：改用绝对定位，外边距不参与布局：

```css
.my-toggle i { position: relative; }
.my-toggle i::after { position: absolute; top: 2px; left: 2px; }
```

**规则**：在"需要精确位置"的小控件里，**用绝对定位，不要用 margin 定位**。
margin 的语义是"和邻居保持距离"，它天然会和父级、兄弟发生合并，
不适合拿来当坐标。

这两条都无法用门禁自动检查（CSS 的"看起来对不对"需要人眼）。
所以 `temp/preview-ui.cjs` 会把弹层模板抽出来生成静态预览页，
改动样式后跑一次、用浏览器看一眼 —— 这是目前唯一可靠的验证方式。

## 三、软规则（评审时看）

### 3.1 函数长度

| 行数 | 判断 |
| --- | --- |
| ≤ 30 | 正常 |
| 30 ~ 80 | 留意，看是否有天然的分段 |
| > 80 | 该拆 |

本项目当前最长 78 行（`background.js:287` `callProvider`）：
六种服务商的请求各写了一段，但**复杂度只有 14** —— 长但不绕。
次席是 `timezone.js:4305` 的 `createRoot`（77 行），
一整个面板的 DOM 模板，拆开反而更难和设计稿逐行对照。
两者都已经落在 80 行以内，不再占用质量预算的豁免名额。

> 更早一轮 `callProvider` 是 89 行、榜首。它降到 78 行，
> 不是因为把代码搬走了，而是**度量口径修了一处缺陷**：
> 原来"函数长度"把整行注释也数进去，这和"注释要写清为什么"（见 3.4）直接打架 ——
> 认真写注释反而被判定为函数变长。现在只数真正的代码行。
> **指标和规范打架时，要怀疑指标。**

### 3.2 圈复杂度

| 复杂度 | 判断 |
| --- | --- |
| ≤ 10 | 正常 |
| 10 ~ 15 | 留意 |
| > 15 | 该拆分支 |

**拆之前先问一句：这些分支是"决策"还是"查表"？**

- 是决策（不同情况做不同的事）→ 拆成小函数
- 是查表（一堆 `if (X) return 常量`）→ **改成数据表**，见第五节

本项目当前最高 24（`options.js:376` `loadSettings`）。

> 长度和复杂度要**分开看**。复杂度低但很长的函数，多半是平铺的模板或分发，
> 拆开不会让任何人更容易理解；复杂度高的函数，无论多短都该拆。

### 3.3 嵌套深度

超过 3 层就该考虑用卫语句提前返回：

```js
// 三层嵌套
function handle(msg) {
  if (msg) {
    if (msg.type === "A") {
      if (msg.payload) {
        doSomething(msg.payload);
      }
    }
  }
}

// 卫语句，零嵌套
function handle(msg) {
  if (!msg) return;
  if (msg.type !== "A") return;
  if (!msg.payload) return;
  doSomething(msg.payload);
}
```

### 3.4 注释写"为什么"，不写"是什么"

```js
// 废话：自增计数器
counter += 1;

// 有用：解释了一个别人猜不到的决定
// 正常情况下每次翻译都会命中同一个域名，无脑写 session storage 等于给每次翻译
// 多加一次存储写入；只在域名真的变了的时候写。
if (googleFreePreferredHost === host) return;
```

判断标准：**读代码就能看出来的不写；"为什么不那样写"必须写。**

### 3.5 断言要描述不变量，不要数调用次数

这是重构里踩出来的坑，值得单独写一条。

`background.js` 有四条聊天翻译出口，它们必须给出同一个结果形状。
这条断言原来是这么写的：

```js
// 错：数某个函数被调用了几次
assert.equal((background.match(/toChatResult\(/g) || []).length, 7,
  '所有翻译出口都要校验');
```

这个数字**两头都不对**：

- **正确重构后会误报。** 把三条出口里各自内联的收尾集中到一个
  `toChatResult()` 里，次数从 7 掉到 4 —— 出口一个没少，反而更不容易漏，
  但测试红了。
- **真正的回归会漏报。** 如果新增一条出口**忘记**走统一收口，
  那个字符串的出现次数根本不会变，测试照样绿。

所以现在的写法是**计数 + 行为**两条一起上，而且计数只数"调用点"：

```js
// 数调用点：排除函数声明本身，这样重构时不会因为多了一行 function 就误报。
assert.equal((background.match(/(?<!function )toChatResult\(/g) || []).length, 4,
  '免费接口 / DeepL 批量 / AI 批量 / 逐条降级 四个出口都要经过 toChatResult');

// 验行为：真的跑一次批量翻译，确认返回的字段就是这两个。
assert.deepEqual(Object.keys(batch[0]).sort(), ['id', 'text'], '出口形状必须是 { id, text }');
```

> **判断标准：这个断言在"代码写得不一样但行为正确"时会不会失败？**
> 会，说明它锁的是**写法**；不会，才说明它锁的是**行为**。
> 如果确实需要锁结构（比如"每个出口都必须经过同一个收口函数"），
> 那就只数**调用点**，并且**必须另配一条行为断言兜底** —— 单靠计数迟早会失灵。

数调用次数、数行数、比较 `Object.keys().length` 这类断言都有同样的毛病。
真要数，数的应该是"有多少个出口"这种**业务事实**，而不是"某段字符串出现了几次"。

> 补充（本轮又踩了一次）：上面那条"数源码里出现几次"的断言在 `withWarnings`
> 那一处虽然改成了行为断言，但**同一个测试里还有一条数 `=> withWarnings(item,`
> 的断言没改**。结果给某个调用点补了个参数、顺手折成多行，它就红了 ——
> 红的不是缺陷，是断言本身在数格式。现在改成只数调用点、不在乎换行：
> `/(?<!function )withWarnings\(/g`。
> **同一类毛病要一次清干净，只改一处等于没改。**

### 3.6 同一套逻辑抄了几份，改的时候一定会漏一份

这是本轮找到的最严重的一类缺陷，出现了两次，值得单列。

**案例一：四条翻译出口，加参数时只加了三处。**（v3.9.10 的缺陷；那个开关本身已在 v3.9.13 移除）

批量翻译有四条通道：AI 批量、DeepL 批量、逐条降级、免费 Google。
新增一个开关时，三条通道加上了参数，AI 批量那条漏了。
表现是：用 DeepL 时开关生效，换成 Gemini 就静默不生效 ——
**不报错、不提示，用户只会觉得"这个开关时灵时不灵"。**

> 开关已随功能移除，但这个坑留着：**新增一条通道时，要回头把已有的每一个参数
> 对着抄一遍。** 现在的做法是四条出口全部收口到同一个 `toChatResult()`，
> 并用"数调用点 + 验行为"两条断言钉住（见 3.5）。

**案例二：同一段条件抄了三遍。**

`options.js` 里判断"这次请求的结果还算不算数"的条件被原样抄了三遍
（模型分支、测试分支、错误分支）：

```js
// 抄了三遍，改的时候漏一个就是"旧请求的结果盖掉新界面的"
if (activeProvider === requestProvider && requestGeneration === providerGeneration
    && actionId === providerActionSequence[kind]) { ... }
```

已经抽成一个函数，三处共用：

```js
function isProviderActionStale(kind, requestProvider, requestGeneration, actionId) {
  return activeProvider !== requestProvider
    || requestGeneration !== providerGeneration
    || actionId !== providerActionSequence[kind];
}
```

**怎么防：**

1. **同一段逻辑出现第二次就该抽。** 不要等第三次 —— 等到第三次时，
   三个人已经各自记了一份不同版本的心智模型。
2. **抽出来的函数要有个能说清"为什么"的名字。** `isProviderActionStale` 比
   `checkProviderState` 好，因为它说明了返回值是什么。
3. **加测试时优先测"每条路径都走同一个出口"**，而不是测"某条路径对不对"。
   上面案例一现在有一条专门的用例：四条通道各跑一遍，断言开关都生效。

### 3.7 不要从界面上读状态，再写回去

`options.js` 的"获取可用模型"按钮原来这么写：

```js
// 错：在请求发起那一刻，把按钮上当时的文字记下来
const original = button.textContent;
button.textContent = "获取中…";
try { ... } finally { button.textContent = original; }   // 再写回去
```

看着很自然，但只要**在请求飞行途中按钮文字被别的代码改过**，这个"记忆"就脏了：

点一次 → 文字变"获取中…" → 请求还没回来时用户切换翻译服务
（按钮被重新启用，但文字没跟着复位）→ 再点一次，这次 `original` 抓到的是
**"获取中…"** → 请求结束后写回去，按钮就永久显示"获取中…"，只能刷新页面。

改法：**文案由业务参数推导，不从界面上读。**

```js
const PROVIDER_ACTION_LABELS = {
  models: { idle: "获取可用模型", busy: "获取中…" },
  test: { idle: "测试连接", busy: "测试中…" }
};
```

**判断标准：这个值的"真相"在代码里，还是在界面上？**
界面上的是**渲染结果**，可能被任何一方改写；代码里的才是**真相**。
凡是要"先读界面、稍后再写回"的地方，先问一句：
如果这期间界面被别人改过，我读到的还是对的吗？

同样的道理适用于：把 `input.value` 读进来存着稍后回填、把 `dataset` 当状态机、
把 CSS class 当布尔标志。

### 3.8 缓存的键必须包含所有影响结果的输入

聊天翻译在内容脚本侧有一个内存缓存。它的键是：

```
provider:model:translationProfile:targetCode:textHash
```

> 这个键原来还带一个 `translationAutoNormalize`（那是个"会改写译文正文"的开关）。
> v3.9.13 把那个开关连同功能一起移除后，它也从键里去掉了。
> **删掉一个输入时，同样要回来看一眼缓存键** —— 否则键里会留下一个
> 永远不变的常量，表面上无害，实际是让人看不懂的死信息。

规则很简单：**只要一个输入会改变输出，它就必须在缓存键里。**
反过来说，检查缓存键有个机械办法 —— 把生成输出的那段代码读一遍，
把里面用到的每一个"外部输入"都列出来，逐个对照缓存键，缺谁补谁。

同一个坑在 `background.js` 的缓存键上也踩过（原来漏了 `baseUrl`，
换自建中转地址后仍命中旧缓存）。两处现在都补齐了。

> 注意这里有个反向的坑：**别把"只是用于展示"的东西塞进缓存键**，
> 那会让缓存命中率无谓地掉下来。判据是"它会不会改变输出"，不是"它变了会不会让人困惑"。

## 四、代码评审怎么做

### 评审者：看这 6 条，按顺序

1. **这次改动有没有测试？** 没有就退回。修 bug 必须有能复现的用例。
2. **有没有改到不该改的地方？** 用 `git diff` 逐行看，不看摘要。
3. **边界条件处理了吗？** 空值、超长、并发、网络失败。
4. **有没有吞异常？** 有就要求写清楚为什么。
5. **命名说得清意图吗？** `data` / `temp` / `result2` 这类名字要求改。
6. **跨文件约定同步了吗？** 参照 2.7 那张表。

### 被评审者：三条纪律

1. **一次 PR 只做一件事。** "顺手重构了一下"是评审者的噩梦。
2. **自己先在本地跑一遍 `npm run check`。** 让机器挑的错不要浪费人的时间。
3. **被指出问题不要辩解，先改，改完再讨论。** 讨论的时机在改完之后，成本低得多。

## 五、一个值得学的重构手法：把 if 链变成数据表

这是本项目最有代表性的一次重构，建议每个人都看一遍。

**重构前**（`timezone.js` `detectSingleLanguage`，复杂度 42）：

```js
if (/[\u3040-\u30ff]/.test(text)) return makeDetectedLanguage("jpn", 1);
if (/[\uac00-\ud7af]/.test(text)) return makeDetectedLanguage("kor", 1);
if (/[\u4e00-\u9fff]/.test(text)) return makeDetectedLanguage("cmn", 1);
if (/[\u0e00-\u0e7f]/.test(text)) return makeDetectedLanguage("tha", 1);
// ... 还有 20 多行
```

**重构后**：

```js
var SCRIPT_LANGUAGES = [
  [/[\u3040-\u30ff]/, () => ["jpn", 1]],
  [/[\uac00-\ud7af]/, () => ["kor", 1]],
  [/[\u4e00-\u9fff]/, () => ["cmn", 1]],
  [/[\u0e00-\u0e7f]/, () => ["tha", 1]],
  // ...
];

function detectByScript(text) {
  for (const [pattern, pick] of SCRIPT_LANGUAGES) {
    if (!pattern.test(text)) continue;
    const picked = pick(text);
    if (picked) return picked;
  }
  return null;
}
```

结果：复杂度 42 → 10，行数 52 → 17，**加一门语言从"改控制流"变成"加一行数据"**。

### 怎么判断一段代码该不该这么改

问自己：**这段 `if` 里，有没有一个分支是"因为另一个分支的存在而存在"的？**

如果没有 —— 每个分支都是独立地"匹配某个模式 → 返回某个常量"，
那它就是数据，只是被写成了代码。

### 两个必须注意的点

1. **表的顺序就是语义。** 原代码从上到下短路，改成表之后顺序必须一致。
   这次重构保留了原顺序，并补了测试钉死。
2. **先补测试再改。** 这个函数当时**一条测试都没有**。
   先加了 4 组用例（见 `temp/regression-checks.cjs` 里 `scriptDetectModule`），
   再动结构。顺序反了，就是"换一种方式犯错"。

### 5.2 案例二：六段几乎一样的循环（原案例的模块已被移除，手法保留）

这个案例原本讲的是 `verify.js` 里"术语 / 柜型 / 型号三类事实的比对逻辑
被手写了六段循环"：六段代码只差**三个东西** —— 读哪个字段、报什么 `kind`、
怎么判断"它在文本里"。改一次措辞要同步改六处，漏一处就是文案不一致，
而且没有任何东西会提醒你。

**`verify.js` 已在 v3.9.13 随功能整体删除，所以那六段代码不再保留** ——
引用一个不存在文件的代码，比删掉它更让人困惑。手法本身是通用的，
抽象出来的形状是这样：

```js
// 六段几乎相同的循环 → 一张表 + 一个循环
const BIDIRECTIONAL_FACTS = [
  {
    field: "incoterms", kind: "incoterm", label: "贸易术语",
    // 每个字段自带"怎么判断它出现在文本里"，差异全部收进数据。
    appearsIn: (facts, text, token) => /* 按字段各自实现 */
  },
  // ... 其余字段同理
];

function compareBidirectionalFacts(source, target, sourceText, translatedText, push) {
  for (const fact of BIDIRECTIONAL_FACTS) {
    for (const token of source[fact.field]) {
      if (!fact.appearsIn(target, translatedText, token)) {
        push(fact.kind, token, `${fact.label} ${token} 在译文里丢失或被改写`);
      }
    }
    for (const token of target[fact.field]) {
      if (!fact.appearsIn(source, sourceText, token)) {
        push(fact.kind, token, `译文出现了原文没有的${fact.label} ${token}`);
      }
    }
  }
}
```

改完之后 `compareHardFacts` 从 53 行 / 复杂度 24 降到 15 行 / 复杂度 1。
**注意改之前它一条测试都没有** —— 先补测试再动结构，顺序不能反（见 5.1）。

### 表的边界在哪 —— 这是最关键的一步

上面那张表只收了"纯粹的双向集合差集"的字段。**其余两类没有塞进去**，
因为它们的逻辑确实不同（下面两条取自已被移除的 `verify.js`，但道理通用）：

- 一类是**折算方向不对称**：某个值在译文里允许换个写法表达
  （比如数字允许写成中文"六层"），那么"丢失"方向要先把别名折算进来，
  "多出"方向反过来只看规范形式 —— 否则"一共""一直"这类常用词会凭空造出数字 1。
- 一类是**符号有多义**：同一个符号可能对应多个候选编码，
  这时判定标准要从"完全相等"放宽成"两边存在共同候选"。

硬凑进表里，就得写 `if (kind === 'number') ... else if (kind === 'currency') ...` ——
那比原来的六段循环更难懂。

> **判断标准：只有当分支之间"只差数据"时才合并。**
> 一旦发现要往表里加特判，就说明它不属于这张表，该单独留一个函数。
>
> 强行统一是比重复更糟的毛病：重复至少还能一眼看出两处不一样，
> 硬凑出来的抽象会把差异藏进 `if` 里。

### 5.3 改完之后，怎么防止它退回去

重构最让人泄气的地方是：改好的地方，下个月又长回去了。

`temp/quality-budget.cjs` 是一道门禁，它把度量变成**可执行的上限**：

| 规则 | 内容 |
| --- | --- |
| R1 | 不在名单里的函数超标 → 拦下（新代码不许开新坑） |
| R2 | 名单里的函数比记录值更差 → 拦下（已有的坑不许再挖深） |
| R3 | 名单里的函数已达标 / 已不存在 → 拦下，**要求删条目** |

上限取 `复杂度 ≤ 15`、`长度 ≤ 80`，和 3.1 / 3.2 的参考线一致。

**R3 是关键。** 没有它，这份名单只会越来越长，最后变成"什么都可以"。
有了它，名单同时是**重构待办清单**：

```
$ npm run test:budget
发现 1 个问题：
  - timezone.js:createRoot 已经达标（复杂度 4 / 77 行），
    请把 ALLOWED 里这一条删掉 —— 名单留着过期的条目就失去意义了
```

这条提示就是 v3.9.11 重构收到的原文。**门禁主动要求你把待办划掉**，
所以名单不会烂，也不会有人假装没看见。

> 还有一条同源的检查：`ALLOWED` 里的条目如果在代码里**找不到**了
> （函数被改名，或整个模块被删掉），门禁同样会拦下，提示"请同步删掉这条"。
> v3.9.13 删 `verify.js` 时就靠它确认名单里没留下指向已删文件的条目 ——
> **删代码时最该信的不是"我记得删干净了"，而是门禁能不能找到残骸。**

> 这条规则值得抄到任何团队：**任何一份"暂时接受的例外清单"，
> 都必须自带一条"什么时候该删掉我"的规则。**
> 否则它一定会变成永久豁免。


## 八、怎么知道测试还有没有用

零、一、五节都在说"先补测试再改"。但还有一个更根本的问题：

**怎么知道已有的测试还有没有用？**

一个团队最容易发生的事不是"没有测试"，而是"有测试，但没人知道它还有没有用"。
测试写了两年，代码改了八轮，中间某一次重构之后某个断言就永远绿着了 ——
它再也没有失败过，也没有人注意到。

覆盖率回答不了这个问题。覆盖率只说明**这行被执行过**，
不说明**这行改坏了会不会被发现**。

唯一能回答的办法是**变异测试**：故意把代码改坏，看测试会不会变红。

```bash
$ npm run test:mutation

[抓住] 后台：批量出口绕过 toChatResult 自己拼对象
       免费接口 / DeepL 批量 / AI 批量 / 逐条降级 四个出口都要经过 toChatResult
[抓住] 弹窗：停用本站不再覆盖子域名
       父域名应当覆盖子域名
[抓住] 聊天：语言缓存不再看置信度门槛
       置信度低于 60 不该写 —— 避免把一次猜测固化下来
...
10 / 10 个变异全部被抓住
```

看到 `[漏掉]` 就是**测试有洞**：那块代码改坏了，回归测试却还是绿的。

### 实现上的三个决定

**① 全程在进程内跑。** 借 `regression-checks.cjs` 暴露的源码覆盖钩子
（`setSourceOverrides`）把文件换成改坏的版本，不起子进程、不动磁盘。
整轮不到 1 秒，所以能当门禁跑。改成起子进程会慢十倍，而且受限环境里根本跑不起来。

**② 判定标准只有一条：改坏后回归测试必须变红。**
不要拿"错误信息里有没有某个关键字"当判定 —— 断言输出里通常不含源码字面量，
那样会把"抓住了"误判成"漏掉"。关键字只用来提示
"确认一下是被对的用例抓住的"，防止出现"恰好被另一个测试兜住"的假阳性。

**③ 锚点失效也算失败。** 锚点是精确字符串，代码一改就可能对不上。
这里放水的话，锚点会慢慢腐烂，最后整份变异测试变成空转 —— 那还不如没有。

```
✗ 变异测试
  详情：
    - 聊天翻译：中文原文不再被跳过（白花钱 + 重复气泡）：锚点在 timezone.js 里出现 0 次（需要恰好 1 次）
      —— 代码改过就同步更新锚点
```

修复只要十秒：把锚点改成新的那行代码。这个摩擦是**故意留的**。

### 什么时候加变异点

不是每行代码都值得。**加在"改坏了但看不出来"的地方**：

- 归一化规则（域名去掉 `www.`、号码的区号归一）
- 阈值判断（置信度 ≥ 60、最多报 6 条、输入长度上限）
- 排除名单（哪些词不算型号、哪些节点不算用户手势）
- 收口函数（所有出口都要走的那个，比如 `toChatResult`）
- **曾经修过的坑**（每修一个 bug，就把它的守卫补一个变异点）

反过来，UI 文案、日志、纯取值器不值得 —— 改坏了测试本来就该绿。

> **删功能时反过来做一遍**：被删的变异点如果还留着，锚点会立刻失效；
> 更隐蔽的是**变异点还在、抓它的用例被删了**。所以删完要顺着名单反查一遍
> "还有谁在抓它" —— v3.9.13 就是这么发现"批量出口绕过收口函数"失去看护的。

> **一句话总结第八节：测试也需要被测试。**
> 这件事听起来奢侈，但成本只有 0.5 秒，而它防的是"整个测试体系悄悄失效"。
