## 零、最重要的一条

**改代码之前，先确认改完你怎么知道它是对的。**

如果答不上来，就先写一个能失败的测试，再改。
这不是流程洁癖 —— 这个项目里已经有过两次"修好 A 弄坏 B"，
都是因为改的时候手上没有能立刻验证的手段。

## 一、提交前必做

```bash
npm run check      # 8 道门禁，约 2.4 秒
```

全绿才提交。这条命令跑的是：

| 门禁 | 防什么 |
| --- | --- |
| 静态检查（ESLint） | 拼错变量、恒真恒假、Promise 返回值写错 |
| 默认值一致性 | 5 份 DEFAULTS 副本漂移 |
| 回归测试（47 项） | 已修过的 bug 重新出现 |
| 审查项（8 项） | 版本号、HTML id、开关默认值不一致 |
| 中转服务冒烟（29 项） | 中转服务的请求/响应契约被改坏 |
| 空 catch 有说明 | 吞掉异常却不写为什么 |
| 质量预算 | 函数越写越长、越写越绕 —— 已经改好的地方再退回去 |
| 变异测试（10 个变异点） | 测试变成摆设 —— 代码改坏了，回归测试却还是绿的 |

**任何一道没过就不要提交。** 更不要用 `--no-verify` 之类的方式绕过 ——
门禁拦住你的那一次，通常正是你本来会漏掉的那个 bug。

后两道门禁的细节见 5.3 和第八节。单独跑某一道：

```bash
npm run test:budget      # 只看质量预算名单
npm run test:mutation    # 只跑变异测试
```

## 二、硬规则（门禁会拦）

### 2.1 不要裸用跨文件全局

`background.js` 里 `providers.js` 和 `verify.js` 是用 `importScripts` 加载的，
它们的全局挂在 `globalThis` 上。**必须带命名空间**：

```js
// 错：裸名，运行时 ReferenceError
const result = verifyTranslation(source, target);

// 对：带命名空间
const result = TLP_VERIFY.verifyTranslation(source, target);
```

`options.js` / `popup.js` **只加载了 `providers.js`，没有 `verify.js`**。
所以在 `options.js` 里写 `TLP_VERIFY` 是运行时错误 —— 表现为"某个按钮点了没反应"，
在浏览器里极难定位。

这条已经被 ESLint 按文件声明锁住了（见 `eslint.config.mjs`），
写错了会直接报 `no-undef`。

### 2.2 数字抽取的正则

从文本里抽数字**必须**用这个形状：

```js
/\d{1,3}(?:[,\u00a0 ]\d{3})+(?:\.\d+)?|\d+(?:\.\d+)?/g
```

**不要**写成 `/\d[\d,\s]*/`。后果是真实的：

```
输入：HR-2400, 20GP
错误正则读出：240020        ← 把两个数粘成了一个
正确正则读出：2400, 20     ← 两个数
```

外贸场景里数字错一位就是事故，而这类错误人眼扫一遍基本发现不了。

### 2.3 中文数字只在"丢失"方向还原

`六` → `6`、`三万` → `30000` 这种还原，**只在"原文有、译文没有"这个方向做**。

反方向（译文里的中文数字还原成阿拉伯数字）不能做，因为：

```
"我们一共出了 3 个柜"  →  "一" 被折成 1  →  凭空多出一个数字 1
"稍等一下"            →  "一" 被折成 1
"一直这样"            →  "一" 被折成 1
```

### 2.4 在线状态的判定顺序不能换

WhatsApp 的在线状态文案里，中文"最后上线时间"**含有"上线"两个字**。
所以判定顺序必须是：

```
1. 正在输入  →  2. 离线文案  →  3. 在线文案
```

先判在线，会把"最后上线时间"误判成"当前在线"。

**这条的通用教训**：当判定条件之间存在包含关系时，**先判更具体的**。

### 2.4.1 读不到就当作没有，不要猜

判定顺序之外还有一层：**认不出来的文本一律不能采用**。

实测踩到的坑：WhatsApp 用图标字体渲染图标，图标名（连字名）本身就是文本。
图标字体没加载时，页面上会原样显示一串 `ic-person-filled`。
原来的实现"取状态行附近第一个有文字的元素"，就把这串内部标识
当成了客户状态显示出来。

现在的做法是白名单：只有匹配得上"在线 / 最后上线 / 正在输入"等已知文案
（`looksLikePresenceText`）才采用，否则返回 `null`，指示灯收起。

**通用教训**：从外部页面抓取信息时，**永远假设你会抓到不该抓的东西**。
默认应该是"不显示"，而不是"显示点什么"。这与"读不到状态就收起指示灯、
不假装离线"是同一个取向 —— 宁可少显示，也不要显示错的。

### 2.5 空 catch 必须写清楚为什么可以吞

```js
// 错：半年后没人敢动这段代码
try { window.focus(); } catch (_) {}

// 对
try { window.focus(); } catch (_) { /* 非用户手势时浏览器会拒绝 */ }
```

说明可以写在 `catch` 前面，也可以写在块内第一行。门禁两头都认。

### 2.6 vendored 代码要用标记圈起来

`timezone.js` 里有 3230 行第三方打包产物（libphonenumber-js + franc）。
它必须用标记圈出来：

```js
/* eslint-disable */
// ===== 以下到第 3231 行是第三方库的打包产物，不要手改，升级时整段替换 =====
...
/* eslint-enable */
// 以下开始是本项目自己的代码
```

不圈起来的话，静态检查和度量都会把第三方代码算成"我们的问题"，
噪音会把真问题淹掉（本项目 3230 行噪音 vs 4074 行自有代码）。

### 2.7 加新设置要同时改 5 处

这是本项目最容易漏的地方。加一个 `watXxx` 设置，必须改：

| # | 文件 | 位置 | 作用 |
| --- | --- | --- | --- |
| 1 | `options.js` | `DEFAULTS` | **权威定义** |
| 2 | `options.js` | `APPEARANCE_DEFAULTS` 或 `CHAT_DEFAULTS` | 恢复默认时遍历用 |
| 3 | `popup.js` | `DEFAULTS` | 弹窗要读的部分 |
| 4 | `timezone.js` | `DISPLAY_DEFAULTS` | 内容脚本要读的部分 |
| 5 | `options.html` | 对应的 `id` | 设置页控件 |

漏掉第 4 处最危险：**不会报错**，只会静默用错默认值。

`npm run check` 里的「默认值一致性」门禁会检查这 5 处的子集关系和取值一致性。
本轮它第一次运行就抓到了 `provider` 默认值不一致。

### 2.8 自定义控件的样式：两个必踩的坑

弹层里的快捷开关（`.wat-toggle`）不报错、也能点，但看起来"像坏的"。
根因是两条 CSS 细节，与控件逻辑无关：

**坑一：选择器优先级 —— 隐藏的 checkbox 被通用规则撑大了**

同一个面板里，文本框和下拉框共用一条规则：

```css
#wat-region-time-root input { height: 34px; padding: 9px; border: 1px solid ...; }
```

这条带 **ID 选择器**，优先级高于给开关写的 `.wat-toggle input`（只有类选择器）。
于是开关里那个 `opacity: 0` 的原生 checkbox 也被撑成 34px 高、加 1px 边框、9px 内边距。
视觉开关只有 18px 高，但**点到它下方 16px 也会切换** —— 用户会觉得"这开关很飘"。

修法：给开关的选择器也加上同样的 ID 前缀，让它的优先级不低于通用规则。

**规则**：写通用元素选择器（`input` / `select` / `button`）时，
先想清楚会不会误伤已有的自定义控件。**ID 选择器的优先级会静默盖掉类选择器**，
不报错、不警告，只能靠肉眼发现。

**坑二：外边距合并 —— 滑块被顶到轨道顶部**

滑块原来用 `margin: 2px` 定位：

```css
.wat-toggle i::after { width: 14px; height: 14px; margin: 2px; }
```

`::after` 是**块级盒子**，它的上外边距会和父元素 `i` 发生
**外边距合并（margin collapsing）**，被一起推到轨道顶部。
结果滑块偏上、不居中，看起来像开关坏了。

修法：改用绝对定位，外边距不参与布局：

```css
.wat-toggle i { position: relative; }
.wat-toggle i::after { position: absolute; top: 2px; left: 2px; }
```

**规则**：在"需要精确位置"的小控件里，**用绝对定位，不要用 margin 定位**。
margin 的语义是"和邻居保持距离"，它天然会和父级、兄弟发生合并，
不适合拿来当坐标。

这两条都无法用门禁自动检查（CSS 的"看起来对不对"需要人眼）。
所以 `temp/preview-ui.cjs` 会把弹层模板抽出来生成静态预览页，
改动样式后跑一次、用浏览器看一眼 —— 这是目前唯一可靠的验证方式。

## 三、软规则（评审时看）

### 3.1 函数长度

| 行数 | 判断 |
| --- | --- |
| ≤ 30 | 正常 |
| 30 ~ 80 | 留意，看是否有天然的分段 |
| > 80 | 该拆 |

本项目当前最长 89 行（`background.js:229` `callProvider`）。
它长是因为六种服务商的请求各写了一段，但**复杂度只有 13** —— 长但不绕。
`timezone.js:4402` 的 `createRoot`（88 行）同理：一整个面板的 DOM 模板，
拆开反而更难和设计稿逐行对照。两者都是**有意保留**的。

### 3.2 圈复杂度

| 复杂度 | 判断 |
| --- | --- |
| ≤ 10 | 正常 |
| 10 ~ 15 | 留意 |
| > 15 | 该拆分支 |

**拆之前先问一句：这些分支是"决策"还是"查表"？**

- 是决策（不同情况做不同的事）→ 拆成小函数
- 是查表（一堆 `if (X) return 常量`）→ **改成数据表**，见第五节

本项目当前最高 24（`options.js:376` `loadSettings`）。

> 长度和复杂度要**分开看**。复杂度低但很长的函数，多半是平铺的模板或分发，
> 拆开不会让任何人更容易理解；复杂度高的函数，无论多短都该拆。

### 3.3 嵌套深度

超过 3 层就该考虑用卫语句提前返回：

```js
// 三层嵌套
function handle(msg) {
  if (msg) {
    if (msg.type === "A") {
      if (msg.payload) {
        doSomething(msg.payload);
      }
    }
  }
}

// 卫语句，零嵌套
function handle(msg) {
  if (!msg) return;
  if (msg.type !== "A") return;
  if (!msg.payload) return;
  doSomething(msg.payload);
}
```

### 3.4 注释写"为什么"，不写"是什么"

```js
// 废话：自增计数器
counter += 1;

// 有用：解释了一个别人猜不到的决定
// 正常情况下每次翻译都会命中同一个域名，无脑写 session storage 等于给每次翻译
// 多加一次存储写入；只在域名真的变了的时候写。
if (googleFreePreferredHost === host) return;
```

判断标准：**读代码就能看出来的不写；"为什么不那样写"必须写。**

### 3.5 断言要描述不变量，不要数调用次数

这是本轮重构里踩出来的坑，值得单独写一条。

`background.js` 有三条翻译出口都必须做硬信息校验。原来的断言是这样的：

```js
// 错：数某个函数被调用了几次
assert.equal((background.match(/TLP_VERIFY\.verifyTranslation\(/g) || []).length, 7,
  '所有翻译出口都要校验');
```

这个数字**两头都不对**：

- **正确重构后会误报。** 把三条出口里各自内联的校验集中到一个
  `withWarnings()` 里，次数从 7 掉到 5 —— 校验一次没少，反而更不容易漏，
  但测试红了。
- **真正的回归会漏报。** 如果新增一条出口**忘记**加校验，
  `verifyTranslation(` 的出现次数根本不会变，测试照样绿。

改成描述**不变量**：

```js
// 对：凡是返回给客户端的译文对象，都必须带 warnings
const exits = background.split('\n')
  .map((line, index) => ({ line: line.trim(), number: index + 1 }))
  .filter(({ line }) => /^return \{ .*\b(?:targetLanguage:|warnings:)/.test(line));
for (const { line, number } of exits) {
  assert.match(line, /\bwarnings:/, `background.js:${number} 的译文出口漏了 warnings`);
}
```

> **判断标准：这个断言在"代码写得不一样但行为正确"时会不会失败？**
> 会，说明它锁的是**写法**；不会，才说明它锁的是**行为**。

数调用次数、数行数、比较 `Object.keys().length` 这类断言都有同样的毛病。
真要数，数的应该是"有多少个出口"这种**业务事实**，而不是"某段字符串出现了几次"。

## 四、代码评审怎么做

### 评审者：看这 6 条，按顺序

1. **这次改动有没有测试？** 没有就退回。修 bug 必须有能复现的用例。
2. **有没有改到不该改的地方？** 用 `git diff` 逐行看，不看摘要。
3. **边界条件处理了吗？** 空值、超长、并发、网络失败。
4. **有没有吞异常？** 有就要求写清楚为什么。
5. **命名说得清意图吗？** `data` / `temp` / `result2` 这类名字要求改。
6. **跨文件约定同步了吗？** 参照 2.7 那张表。

### 被评审者：三条纪律

1. **一次 PR 只做一件事。** "顺手重构了一下"是评审者的噩梦。
2. **自己先在本地跑一遍 `npm run check`。** 让机器挑的错不要浪费人的时间。
3. **被指出问题不要辩解，先改，改完再讨论。** 讨论的时机在改完之后，成本低得多。

## 五、一个值得学的重构手法：把 if 链变成数据表

这是本项目最有代表性的一次重构，建议每个人都看一遍。

**重构前**（`timezone.js` `detectSingleLanguage`，复杂度 42）：

```js
if (/[\u3040-\u30ff]/.test(text)) return makeDetectedLanguage("jpn", 1);
if (/[\uac00-\ud7af]/.test(text)) return makeDetectedLanguage("kor", 1);
if (/[\u4e00-\u9fff]/.test(text)) return makeDetectedLanguage("cmn", 1);
if (/[\u0e00-\u0e7f]/.test(text)) return makeDetectedLanguage("tha", 1);
// ... 还有 20 多行
```

**重构后**：

```js
var SCRIPT_LANGUAGES = [
  [/[\u3040-\u30ff]/, () => ["jpn", 1]],
  [/[\uac00-\ud7af]/, () => ["kor", 1]],
  [/[\u4e00-\u9fff]/, () => ["cmn", 1]],
  [/[\u0e00-\u0e7f]/, () => ["tha", 1]],
  // ...
];

function detectByScript(text) {
  for (const [pattern, pick] of SCRIPT_LANGUAGES) {
    if (!pattern.test(text)) continue;
    const picked = pick(text);
    if (picked) return picked;
  }
  return null;
}
```

结果：复杂度 42 → 10，行数 52 → 17，**加一门语言从"改控制流"变成"加一行数据"**。

### 怎么判断一段代码该不该这么改

问自己：**这段 `if` 里，有没有一个分支是"因为另一个分支的存在而存在"的？**

如果没有 —— 每个分支都是独立地"匹配某个模式 → 返回某个常量"，
那它就是数据，只是被写成了代码。

### 两个必须注意的点

1. **表的顺序就是语义。** 原代码从上到下短路，改成表之后顺序必须一致。
   这次重构保留了原顺序，并补了测试钉死。
2. **先补测试再改。** 这个函数当时**一条测试都没有**。
   先加了 4 组用例（见 `temp/regression-checks.cjs` 里 `scriptDetectModule`），
   再动结构。顺序反了，就是"换一种方式犯错"。

### 5.2 案例二：`verify.js` 的双向比对 —— 同一手法的另一种形态

上面那个案例是"一堆分支只差常量"。还有一种更常见的情况：
**一堆分支的代码完全一样，只是操作的数据不同。**

`verify.js` 里，术语 / 柜型 / 型号三类事实的比对逻辑是这样写的（六段循环）：

```js
for (const term of source.incoterms) {
  if (!incotermAppearsIn(translatedText, term)) push("incoterm", term, `贸易术语 ${term} 在译文里丢失或被改写`);
}
for (const term of target.incoterms) {
  if (!incotermAppearsIn(sourceText, term)) push("incoterm", term, `译文出现了原文没有的贸易术语 ${term}`);
}
for (const size of source.containers) {
  if (!target.containers.has(size)) push("container", size, `柜型 ${size} 在译文里丢失或被改写`);
}
// ... 柜型反向、型号双向，一共六段
```

六段代码只差**三个东西**：读哪个字段、报什么 `kind`、怎么判断"它在文本里"。
改一次措辞要同步改六处，漏一处就是文案不一致 —— 而且没有任何东西会提醒你。

改成一张表 + 一个循环：

```js
const BIDIRECTIONAL_FACTS = [
  {
    field: "incoterms", kind: "incoterm", label: "贸易术语",
    // 术语可能被意译成中文（EXW → 出厂价），必须回到文本里找，不能只看抽取结果。
    appearsIn: (facts, text, token) => incotermAppearsIn(text, token)
  },
  {
    field: "containers", kind: "container", label: "柜型",
    // 抽取时已把 HC 归一到 HQ、中文柜型归一到 GP，直接比集合就够了。
    appearsIn: (facts, text, token) => facts.containers.has(token)
  },
  { field: "models", kind: "model", label: "型号",
    appearsIn: (facts, text, token) => facts.models.has(token) }
];

function compareBidirectionalFacts(source, target, sourceText, translatedText, push) {
  for (const fact of BIDIRECTIONAL_FACTS) {
    for (const token of source[fact.field]) {
      if (!fact.appearsIn(target, translatedText, token)) {
        push(fact.kind, token, `${fact.label} ${token} 在译文里丢失或被改写`);
      }
    }
    for (const token of target[fact.field]) {
      if (!fact.appearsIn(source, sourceText, token)) {
        push(fact.kind, token, `译文出现了原文没有的${fact.label} ${token}`);
      }
    }
  }
}
```

结果：`compareHardFacts` 复杂度 24 → 1，行数 53 → 15。

### 表的边界在哪 —— 这是最关键的一步

数字和货币**没有**塞进上面这张表。它们的逻辑确实不同：

- 数字：译文允许写成中文（"6-layer" → "六层"），所以"丢失"方向要先把中文数字折算进来；
  "多出"方向反过来只看阿拉伯数字，否则"一共""一直"会凭空造出数字 1。
- 货币：符号 `$` 有多义（USD / AUD / CAD / HKD ...），两边**有一个共同候选**就算一致。

硬凑进表里，就得写 `if (kind === 'number') ... else if (kind === 'currency') ...` ——
那比原来的六段循环更难懂。

> **判断标准：只有当分支之间"只差数据"时才合并。**
> 一旦发现要往表里加特判，就说明它不属于这张表，该单独留一个函数。
>
> 强行统一是比重复更糟的毛病：重复至少还能一眼看出两处不一样，
> 硬凑出来的抽象会把差异藏进 `if` 里。

### 5.3 改完之后，怎么防止它退回去

重构最让人泄气的地方是：改好的地方，下个月又长回去了。

`temp/quality-budget.cjs` 是一道门禁，它把度量变成**可执行的上限**：

| 规则 | 内容 |
| --- | --- |
| R1 | 不在名单里的函数超标 → 拦下（新代码不许开新坑） |
| R2 | 名单里的函数比记录值更差 → 拦下（已有的坑不许再挖深） |
| R3 | 名单里的函数已达标 / 已不存在 → 拦下，**要求删条目** |

上限取 `复杂度 ≤ 15`、`长度 ≤ 80`，和 3.1 / 3.2 的参考线一致。

**R3 是关键。** 没有它，这份名单只会越来越长，最后变成"什么都可以"。
有了它，名单同时是**重构待办清单**：

```
$ npm run test:budget
发现 1 个问题：
  - verify.js:compareHardFacts 已经达标（复杂度 1 / 15 行），
    请把 ALLOWED 里这一条删掉 —— 名单留着过期的条目就失去意义了
```

这条提示就是本轮重构收到的原文。**门禁主动要求你把待办划掉**，
所以名单不会烂，也不会有人假装没看见。

> 这条规则值得抄到任何团队：**任何一份"暂时接受的例外清单"，
> 都必须自带一条"什么时候该删掉我"的规则。**
> 否则它一定会变成永久豁免。

## 八、怎么知道测试还有没有用

零、一、五节都在说"先补测试再改"。但还有一个更根本的问题：

**怎么知道已有的测试还有没有用？**

一个团队最容易发生的事不是"没有测试"，而是"有测试，但没人知道它还有没有用"。
测试写了两年，代码改了八轮，中间某一次重构之后某个断言就永远绿着了 ——
它再也没有失败过，也没有人注意到。

覆盖率回答不了这个问题。覆盖率只说明**这行被执行过**，
不说明**这行改坏了会不会被发现**。

唯一能回答的办法是**变异测试**：故意把代码改坏，看测试会不会变红。

```bash
$ npm run test:mutation

[抓住] 硬信息：柜型 HC 不再归一到 HQ
       Expected values to be strictly deep-equal:
[抓住] 后台：译文出口丢掉 warnings
       background.js:758 的译文出口漏了 warnings
[抓住] 弹窗：停用本站不再覆盖子域名
       父域名应当覆盖子域名
[抓住] 聊天：语言缓存不再看置信度门槛
       置信度低于 60 不该写 —— 避免把一次猜测固化下来
...
10 / 10 个变异全部被抓住
```

看到 `[漏掉]` 就是**测试有洞**：那块代码改坏了，回归测试却还是绿的。

### 实现上的三个决定

**① 全程在进程内跑。** 借 `regression-checks.cjs` 暴露的源码覆盖钩子
（`setSourceOverrides`）把文件换成改坏的版本，不起子进程、不动磁盘。
整轮约 0.5 秒，所以能当门禁跑。改成起子进程会慢十倍，而且受限环境里根本跑不起来。

**② 判定标准只有一条：改坏后回归测试必须变红。**
不要拿"错误信息里有没有某个关键字"当判定 —— 断言输出里通常不含源码字面量，
那样会把"抓住了"误判成"漏掉"。关键字只用来提示
"确认一下是被对的用例抓住的"，防止出现"恰好被另一个测试兜住"的假阳性。

**③ 锚点失效也算失败。** 锚点是精确字符串，代码一改就可能对不上。
这里放水的话，锚点会慢慢腐烂，最后整份变异测试变成空转 —— 那还不如没有。

```
✗ 变异测试
  详情：
    - 硬信息：柜型 HC 不再归一到 HQ：锚点在 verify.js 里出现 0 次（需要恰好 1 次）
      —— 代码改过就同步更新锚点
```

修复只要十秒：把锚点改成新的那行代码。这个摩擦是**故意留的**。

### 什么时候加变异点

不是每行代码都值得。**加在"改坏了但看不出来"的地方**：

- 归一化规则（`HC` → `HQ`、`RMB` → `CNY`）
- 阈值判断（置信度 ≥ 60、最多报 6 条）
- 排除名单（`USD12` 不算型号）
- 收口函数（所有出口都要走的那个）

反过来，UI 文案、日志、纯取值器不值得 —— 改坏了测试本来就该绿。

> **一句话总结第八节：测试也需要被测试。**
> 这件事听起来奢侈，但成本只有 0.5 秒，而它防的是"整个测试体系悄悄失效"。
