### 同日：免费档"能用但慢"的性能优化

- 用户反馈：Google 免费档可用但翻译很慢。定位到的根因与改动：
  1. **串行探测域名 + 20 秒超时**（最坏 3×20=60 秒）：改为「记住上次成功域名（内存 + `chrome.storage.session` 持久化，跨 SW 重启有效）→ 命中则单发一个请求；未命中或失败则**并行**探测其余域名」。超时 20s → 首次 6s / 探测 10s。最坏等待降到十几秒，正常情况 1 个请求。
  2. **输入框翻译完全没有缓存**：新增 `translationCache`（LRU 200，键含服务/接口地址/模型/翻译专家/场景/目标语言/原文）。**只缓存确定性引擎**（`CACHEABLE_ADAPTERS = googlefree, deepl`），AI 服务不缓存以便用户重新生成。命中时返回 `cached: true`。
  3. 免费档聊天批量并发 3 → 4。
- 测试：回归 **22/22**。为可确定性断言，`backgroundContext` 增加第三个参数 `sessionOverrides`（并补了 `storage.session.set` mock），可用 `{ googleFreeHost: 'translate.googleapis.com' }` 固定首选域名；新增用例：429 后并行探测、记住成功域名（第二次只发 1 个请求）、重复翻译命中缓存、AI 服务不缓存。删除了旧的串行 429 用例（已被并行用例取代）。

### 同日：翻译中转方案（Cloudflare Worker）

- 背景：免费档在国内能否用取决于节点，前端无解；唯一可靠解法是自建中转。用户问"做中转要怎么做"。

- 已核实扩展端的两处前提（决定了路径令牌方案可行）：
  - `background.js` `googleFreeHosts(provider)`：把用户填的 `baseUrl` 放在首位，**后面仍跟 3 个 Google 官方域名做回退** → 中转挂了不会直接不可用（有 VPN 时仍能翻），国内直连时中转是唯一通路。

- 新增 `relay/`：
  - `worker.js`：多上游依次重试（`translate.googleapis.com` → `translate.google.com` → `clients5.google.com`）；`caches.default` 边缘缓存 30 天；`ctx.waitUntil` 异步写缓存不阻塞响应；CORS；可选 `RELAY_TOKEN`；`/health`；文本上限 2000。
  - **令牌支持路径传法**（`/t/<token>/translate_a/single`）——这是关键，因为扩展无法方便地加自定义请求头，而查询串传法会被拼在 `/translate_a/single` 之前失效。用 `splitTokenPath()` 取出令牌，**转发上游时剥掉令牌**。

  - `wrangler.toml`（含自定义域名 `custom_domain` 与子路径 routes 两种示例）、`README.md`（部署/绑域名/令牌/扩展配置/验证/成本/风险/换平台/FAQ）。

## 同日：源码审查（发现既有严重 BUG）+ WhatsApp 聊天翻译改为常开（v3.9.4）

- 用户需求：① 审查源码找新 BUG ② 把 WhatsApp 聊天翻译常开（开关按钮保留）。
- **审查方式**：自己核对关键路径 + 起了一个独立 Explore agent 复审，后者发现了我漏掉的高危项。**结论：独立复审有效，值得沿用。**
- **发现的真 BUG（既有，非本次引入）**：
  1. 【高】**Azure OpenAI 完全无法使用**。`providers.js` 的 `TLP_ADAPTERS_WITHOUT_MODEL` 漏了 `"azure"`，
     而 Azure 的请求体**根本不发 model**（模型由 baseUrl 里的 `/deployments/<名字>/` 决定，`background.js` 的 azure 分支确认），
     于是填好地址 + Key 仍报「请填写 Azure OpenAI 的模型名称」；同时 `options.js` 还会把模型输入框设为可用（填了也没用）。
  2. 【中】azure 分支硬编码 `max_tokens` + `temperature`，绕过了 `usesCompletionTokenBudget`；
     Azure 上部署 GPT-5 / o 系列会因不认这两个参数而 400。
  3. 【低】`glm` 的 help 写"只想用免费模型请选上一项"，但下拉里它的上一项是 qwen，不是 glmfree。
- **修复**：
  - `TLP_ADAPTERS_WITHOUT_MODEL` 补 `"azure"`。
  - 新增 `azureDeploymentName(baseUrl)`（正则取 `/deployments/([^/?#]+)`），`usesCompletionTokenBudget` 对 azure 改用它判断；
    azure 分支改用与 OpenAI 相同的参数分支逻辑。
- **WhatsApp 常开实现**（timezone.js 4 处 + options.js 2 处 + options.html 2 处）：
  - `DISPLAY_DEFAULTS.watChatTranslationEnabled` false → true；`options.js` 的 DEFAULTS 同步，读取改为 `!== false`。
  - 新增 `chatTranslationAutoActivated` 标志：配置加载时若开关为 true 且未自动激活过 → 置 `chatTranslationSessionActive = true`
    并调 `translateVisibleChat`。**标志是关键**：否则用户按快捷键关掉后，下一次 DOM 变化又会被自动打开，快捷键的"关闭"就失效了。
  - `chrome.storage.onChanged` 改为：开关**有任何变化**就重置该标志，让"关掉再打开"能重新进入常开。
  - options.html 开关文案「允许快捷键」→「聊天翻译常开」，`shortcutHint` 与 安装说明.txt 同步。
  - **循环安全验证**：插入的译文节点带 `data-tlp-chat-translation="1"`，会被 MutationObserver 的 `meaningful` 判断过滤掉，
    所以"插入译文 → DOM 变化 → update → 再翻译"不会形成死循环。
- 测试：回归 **25 → 28**（新增：Azure 不填模型名可用、Azure 上 GPT-5 用 max_completion_tokens、聊天翻译默认开启且不依赖快捷键）；
  review 4/4；relay 29/29；6 个 js 文件 `node --check` 全过。
