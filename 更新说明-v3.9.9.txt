TransMate v3.9.9 更新说明
发布日期：2026-09-29

这一版主要是"工程质量"升级：把原来靠人记住的规则，改成机器自动检查。
功能上的改动很小，但对后续维护影响很大。

TransMate 3.9.9 更新

1. 修复：新装用户的服务商默认值在三个地方不一致（设置页是"未选择"、
   内容脚本被当成"已选 Gemini"）。这个不一致不会报错，只会偶尔走错服务商，
   表现为"有时候翻译结果不太对"，很难查。现在三处已对齐。

2. 优化：语言识别、时区显示、翻译调度等逻辑做了重构，行为完全不变
   但更容易维护。全项目最复杂的函数从 32 降到 24，最长的从 115 行降到 97 行。

3. 内部：加入自动化检查。以后每次改代码，提交前会自动跑 8 道检查
   （静态检查 / 默认值一致性 / 回归测试 47 项 / 审查项 / 中转服务冒烟 /
   空异常说明 / 质量预算 / 变异测试），不合格的改动进不来。

本次不新增浏览器权限，更新后不需要重新授权，使用方式和上一版完全一样。

一、修复：服务商默认值三处不一致

  timezone.js（内容脚本）里把"用户还没选过服务商"的默认值写成了 "gemini"，
  而设置页和后台的权威定义是 ""（空字符串，表示"没选过，稍后再解析"）。

  后果：全新安装的用户，内容脚本会以为自己用的是 Gemini，
  而设置页和后台会按"没选过"的规则解析成免费档。
  两边判断不一致，但不会抛任何错误，只会在缓存指纹上体现出来，
  极难定位。现在统一成 ""，由使用处已有的兜底逻辑接管。

  这个问题是新增的"默认值一致性检查"第一次运行时自动发现的。

二、重构：把"伪装成代码的数据表"还原成数据

  这一类重构做了两处，共同点是：代码里写了一大堆分支，但分支之间
  没有真正的"决策"，只是在查表或做同样的操作。

  ① 语言识别（timezone.js 的 detectSingleLanguage）

  原本是全项目最复杂的函数（复杂度 42），内容是 20 多个这样的分支：

      if (/[\u3040-\u30ff]/.test(text)) return makeDetectedLanguage("jpn", 1);
      if (/[\uac00-\ud7af]/.test(text)) return makeDetectedLanguage("kor", 1);
      ...

  这些分支只是在查一张固定的 Unicode 码位表 —— 它本质上是数据，
  只是被写成了代码。现在改成了表 + 一个循环：

      var SCRIPT_LANGUAGES = [
        [/[\u3040-\u30ff]/, () => ["jpn", 1]],
        [/[\uac00-\ud7af]/, () => ["kor", 1]],
        ...
      ];

  效果：复杂度 42 → 10，行数 52 → 17，加一门语言从"改控制流"变成"加一行数据"。

  ② 硬信息校验（verify.js）

  这是防止"40HQ 被翻译成 40GP""USD 12.5 被写成 12.50"这类事故的功能。
  它原来有两个 53 行的函数，每个都手写了一遍五种事实类型（数字 / 贸易术语 /
  货币 / 柜型 / 型号）的处理，六段循环只差一个字段名和一句提示文案 ——
  改一次措辞要同步改六处，漏一处就是提示不一致。

  现在改成"每种事实一个函数"+"一张表驱动"，两个函数的复杂度从 17 和 24
  降到 3 和 1。

  注意：数字和货币没有被塞进那张表。因为数字要做中文数字折算、
  货币要做符号多义展开，逻辑确实不同 —— 硬凑进去反而更难懂。

三、重构：把巨型函数拆成"一次只做一件事"

  另外三处最影响维护的函数：

  · popup.js 的 render          41 行 / 复杂度 31 → 拆成 5 个分区函数
  · timezone.js 的 update       94 行 / 复杂度 32 → 拆成 5 个函数
  · background.js 的批量翻译     115 行 / 复杂度 22 → 47 行 / 复杂度 8

  三处都是"读配置、算状态、渲染界面、处理失败"全挤在一个函数里，
  要改其中任何一步都得先把整块读完。

  顺带修掉一个隐患：批量翻译原来有三条出口，各自内联拼一遍
  "译文 + 校验结果"。校验逻辑散在三处，新增一条出口时很容易漏加。
  现在集中到一个收口函数，漏不掉。

  这三处重构改完之后，**文件的代码行数都是上涨的**（拆函数本身要写更多行），
  但最长函数和最复杂函数都降了。这也是为什么不拿"代码行数"当质量指标。

四、内部：加入自动化质量门禁

  以前所有质量把关 100% 靠人记住"要手动跑哪个命令"，没有版本控制，
  也没有 CI。现在补齐了：

  · 版本控制     项目首次纳入 git，有 .gitignore / .gitattributes
  · 一键门禁     npm run check —— 8 道检查，约 2.4 秒跑完
  · 持续集成     .github/workflows/quality-gate.yml，每次推送自动跑
  · 质量度量     npm run metrics —— AST 级统计函数长度、复杂度、重复代码

  8 道门禁分别是：

    1. 静态检查（ESLint）      拼错变量、恒真恒假、Promise 返回值写错
    2. 默认值一致性            5 份 DEFAULTS 副本漂移（本次抓到真问题）
    3. 回归测试（47 项）       已修过的 bug 重新出现
    4. 审查项（8 项）          版本号、HTML id、开关默认值不一致
    5. 中转服务冒烟（29 项）   中转服务的请求/响应契约被改坏
    6. 空 catch 有说明         吞掉异常却不写为什么
    7. 质量预算                函数越写越长、越写越绕
    8. 变异测试                测试变成摆设（见下）

  后两道是本次新增的，值得单独说一下：

  【质量预算】度量本身不拦人 —— 谁都不会因为"复杂度 32"被拦下。
  这道门把度量变成可执行的上限：新代码不许超标；已经超标但暂时接受的
  位置要登记在名单里并写清"打算怎么改"；一旦改好了，
  门禁会主动要求把名单里那一条删掉。

  最后这条很关键。没有它，名单只会越来越长，最后变成"什么都可以"。
  本次三处重构各自都被门禁提醒"你已经达标了，把名单里这条删掉"。

  【变异测试】前面几道门都在说"要补测试"，但怎么知道补的测试有用？
  覆盖率回答不了 —— 它只说明"这行被执行过"，不说明"这行改坏了会不会被发现"。

  变异测试的做法是故意把代码改坏，看测试会不会红。本次登记了 10 个
  变异点（柜型归一、数字抽取正则、货币符号多义、校验收口……），
  全部能被抓住。如果哪天某个变异显示"漏掉"，就说明那块逻辑
  已经没有测试保护了。

  这道门防的是一件事：**测试变成摆设**。一个团队最容易发生的不是
  "没有测试"，而是"有测试，但没人知道它还有没有用"。

五、内部：给"吞掉异常"的地方补上说明

  全项目有 12 处空的 catch 块。空 catch 本身不一定是错的
  （很多地方确实"失败了也无所谓"），问题是没写清楚为什么无所谓 ——
  半年后接手的人不敢删也不敢改。现在 12 处全部补上理由，
  并加进门禁：以后新写的空 catch 不写说明会被拦下。
