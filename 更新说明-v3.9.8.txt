TransMate 3.9.8 更新

1. 修复：上一版的"硬信息核对"有两类误报，实际都是翻译得对却被标出来：
   · 模型把 6-layer 正当地译成"六层"，却被报"原文的数字 6 没有出现在译文里"；
   · 模型把 EXW 正当地译成"出厂价"，却被报"贸易术语 EXW 在译文里丢失或被改写"。
   现在中文数字（六 = 6、三万 = 30000）和贸易术语的中文说法
   （出厂价 = EXW、离岸价 = FOB、到岸价 = CIF 等）都会正确识别，
   真的丢数字、真的把 CIF 写成 CFR 依然会报。

2. 新增：客户在线状态指示灯。标签上多一个小圆点——绿色表示客户在线、灰色表示离线；
   客户从离线变成在线时会闪几下，方便抓住客户刚好在线的时机。
   状态直接读 WhatsApp 自己显示的那一行，不额外发任何请求。

3. 新增：弹层里加了两个快捷开关（状态 / 沟通时间），点开标签就能随手开关，
   不用再跑去设置页。设置页里也各有一个，两边同步。

本次不新增浏览器权限，更新后不需要重新授权。

一、修复上一版"硬信息核对"的两类误报

3.9.7 引入的核对功能方向是对的，但报得太急，把"翻译得好"也当成了问题。
两个实测案例：

1. 数字被正当地写成中文

   原文 "6-layer" 译成"六层"，完全正确，但阿拉伯数字 6 在译文里"消失"了，
   于是报"原文的数字 6 没有出现在译文里"。

   现在会把译文里的中文数字还原成阿拉伯数字再比对：
   六 = 6、十五 = 15、二十三 = 23、三万 = 30000、一百零五 = 105。
   所以"6 层"→"六层"、"500 pcs"→"五百件"都不再报。

   注意这里只在"原文的数字有没有丢"这个方向上做补偿。
   反方向（译文多出数字）仍然只看阿拉伯数字——否则"一共""一些""一直"里的"一"
   会凭空造出一堆数字，全是误报。
   数字真的丢了（500 pcs → 件）依然会报。

2. 贸易术语被意译成中文

   原文 "Цена EXW $6,120" 译成"出厂价 $6,120"，EXW 的英文缩写确实没了，
   但"出厂价"就是 EXW 的标准中文说法，翻译是对的，不该报。

   现在每个术语都带一组可接受的中文说法：
     出厂价 = EXW        离岸价 = FOB        到岸价 = CIF
     成本加运费 = CFR     货交承运人 = FCA    船边交货 = FAS
     运费付至 = CPT       运费和保险费付至 = CIP
     目的地交货 = DAP     卸货地交货 = DPU    完税后交货 = DDP
   反向也一样：原文写"出厂价"、译文写 EXW，同样不报。

   但"把 CIF 写成 CFR"这类真正的改写仍然会报——CIF 的别名里没有"成本加运费"。

二、新增：客户在线状态指示灯

1. 怎么用

   · 标签最前面多一个小圆点：绿色 = 客户在线，灰色 = 客户离线。
   · 客户从离线变成在线时，圆点会闪几下，鼠标悬停能看到完整状态文案。
   · 弹层里多了一行"状态"，显示 WhatsApp 原文案，例如"在线"或
     "最后上线时间 昨天 21:10"。

2. 为什么不用额外请求

   状态直接读 WhatsApp 标题下方本来就显示的那一行，不联网、不消耗任何额度，
   也不会让客户察觉。WhatsApp 显示什么，这里就显示什么。

3. 边界（很重要）

   能看到的只有 WhatsApp 自己愿意公开的状态。对方把"最后上线"设成
   仅联系人可见、或完全隐藏时，WhatsApp 页面上就没有这一行，
   这时指示灯会自动收起，不会假装成"离线"。

   另外"最后上线时间"里也含"上线"两个字，判断时已经先排掉离线文案，
   不会把离线误判成在线。客户"正在输入…"时也算在线。

三、新增：弹层里的快捷开关

   · "状态"和"沟通时间"两行末尾各有一个开关，点开标签就能随手开关，
     不用再跑去设置页。
   · 两个开关与设置页共用同一份设置，改完立即生效，两边始终同步。
   · 设置页「客户地区与当地时间」里也各有一个，默认都打开。

四、测试

· 回归测试 35 项 → 36 项。本次把两类误报的实测案例直接写成了用例：
  6-layer → 六层不报、EXW → 出厂价不报、500 → 五百不报、
  "一共 500 件"里的"一"不能凭空造数字、CIF → CFR 仍要报、
  EXW 真的丢掉仍要报；以及在线状态的一整套判定
  （"最后上线时间"不能被当成"在线"、换联系人不能误闪、关掉开关要收起）。
· review 验证脚本 8 项通过，遗留项保持清零。
· relay 冒烟 29 项通过；7 个 js 文件语法检查通过。
· 用真实浏览器渲染了弹层的三种状态（在线+非工作时段 / 离线+工作时段+开关全关 /
  WhatsApp 不公开状态），核对布局与配色。
· 版本号：3.9.7 → 3.9.8

【已知的、尚未处理的问题】
════════════════════════════════════════

以下问题本次没有改，因为改动会改变现有行为，需要先确认：

1. 目标语言是中文时，自己发出的中文消息也会被送去"翻译成中文"。

   聊天翻译默认范围是"收到与发出的消息"，而跳过逻辑在目标语言为中文时直接放行，
   原因是中文识别无法区分简体与繁体，跳过会漏掉需要简繁转换的消息。
   副作用是自己写的中文消息也会占用一次 API 调用，并显示一条几乎相同的"译文"。
   如果想避免，可以先把范围改成"仅客户发来的消息"。

2. 聊天翻译会话开启期间，每次聊天区变化都会重新扫描全部已加载消息。

   长会话（几百条消息）下会有可感知的开销。可以改成只重扫发生变化的那几条，
   属于结构改动，本次未动。

3. 长输入没有预检。

   超长文本会先发出去、被服务商拒绝，再走分片重试。可以先按字符数预判，
   省掉一次注定失败的请求。

4. 推理模型的 token 预算里包含推理 token。

   预算按"可见输出"估算，但 GPT-5 / o 系列会先花掉一部分 token 用于推理，
   极端情况下可能因为预算不够而被截断。需要按模型类型分别估算。

5. 硬信息核对仍然只能做到"提示"，不能自动纠正。

   这是刻意的：数字和术语一旦被自动改错，后果比不提示严重得多。
   所以命中一律显示"请核对"，改不改由人来决定。
